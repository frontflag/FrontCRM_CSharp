# 内外版本日志 — 设计与实现

**适用范围：** FrontCRM（CRM.Web）前端构建版本追溯、部署核对、面向用户的版本说明。  
**关联文档：** [Debug 页 PRD](../PRD/Debu页.md)、[扩展面板.帮助规范](../PRD/规范/UI规范/扩展面板.帮助规范.md)、[Debug 页 AI 模块](../System/AI模块架构与实现.md) §8.3  
**维护说明：** 调整路由、权限、post-commit 行为或对外页样式时，须同步更新本文与 `Debu页.md`。

---

## 1. 设计目标

| 目标 | 说明 |
|------|------|
| **部署可核对** | 运维/开发可在免登录 Debug 页看到「当前前端构建版本」，与 Git 最近一次有效提交对齐 |
| **内部可追溯** | 系统管理员可查看按提交时间倒序的完整内部日志（含每次 commit subject） |
| **对外可阅读** | 业务用户可在免登录页阅读经产品/实施整理的用户向更新说明 |
| **双轨分离** | 内部日志 **全自动**（post-commit）；外部日志 **手工维护** Markdown，避免把 commit message 直接暴露给用户 |
| **与帮助体系统一** | 对外内容存放在 `help/pages/`，经 `sync-help` 同步；注册表驱动帮助面板与 `/release-notes` 共用同一源文件 |

---

## 2. 双轨模型

| 维度 | 内部版本日志 | 外部版本日志 |
|------|--------------|--------------|
| **受众** | 开发、运维、系统管理员 | 全体用户（含未登录访客） |
| **维护方式** | Git `post-commit` 自动写入 | 人工编辑 Markdown |
| **数据源** | `internal-version-log.txt` + `debugConstants.ts` | `help/pages/version/版本更新日志_MENU_RELEASE_NOTES.md` |
| **展示入口** | `/debug`（仅当前版本号）、`/debug/internal-version-log`（全文） | `/release-notes` |
| **登录要求** | 主 Debug 页免登录；内部全文页需登录且 `isSysAdmin` | 免登录 |
| **版本号格式** | `1.1.{MMdd}-{HHmm} {Git commit subject}` | 无统一版本号；按 **日期 + 功能标题** 组织条目 |
| **日志行格式** | `YYYY-MM-DD HH:mm:ss \| {subject}` | Markdown 标题与列表（见 §4.2） |
| **历史回填** | 不支持；自功能上线后逐 commit 累积 | 按发布批次手工追加 |

## 3. 内部版本日志

### 3.1 功能要求

1. **每次有效 Git 提交**后，在 commit 完成时自动：
   - 在 `internal-version-log.txt` **首行 prepend** 一条记录；
   - 更新 `debugConstants.ts` 中的 `FRONTEND_DEBUG_VERSION`；
   - 将上述两文件 `git add` 并以 **`git commit --amend --no-edit --no-verify`** 并入**同一提交**（不产生额外 commit）。
2. **Debug 主列表**（`/debug`）展示 `FRONTEND_DEBUG_VERSION`，用于核对线上是否为本次构建。
3. **内部全文页**（`/debug/internal-version-log`）展示当前版本号 + 全部内部日志行（新 → 旧）。
4. **不追溯历史**：功能启用前的 commit 不会写入；空文件时提示「下次提交后将自动写入」。

### 3.2 版本号与日志格式

- **展示版本号**（`FRONTEND_DEBUG_VERSION`）：  
  `1.1.{MMdd}-{HHmm} {Git commit subject}`  
  其中 `{MMdd}-{HHmm}` 取 **commit 作者日期** 的本地时区月日与时分（`git log -1 --format=%ci`）。
- **内部日志行**：  
  `YYYY-MM-DD HH:mm:ss | {subject}`  
  时间同样来自 `%ci`，秒位补零。

示例：

```
2026-07-05 17:37:14 | fix: post-commit 版本日志脚本兼容 Windows git format
```

对应 `FRONTEND_DEBUG_VERSION`：

```
1.1.0705-1737 fix: post-commit 版本日志脚本兼容 Windows git format
```

### 3.3 跳过与防循环

| 条件 | 行为 |
|------|------|
| 环境变量 `SKIP_INTERNAL_VERSION_LOG=1` | 脚本直接退出（amend 阶段注入，防止二次触发） |
| commit subject 以 `chore: 内部版本日志` 或 `chore: internal version log` 开头（不区分大小写） | 跳过 |
| 日志首行已与本次 commit 相同且 `debugConstants.ts` 已含对应版本字符串 | 跳过（post-commit 重入保护） |

### 3.4 自动化实现

| 项 | 路径 / 说明 |
|----|-------------|
| Husky 钩子 | `.husky/post-commit` → `node scripts/update-internal-version-log.mjs` |
| 更新脚本 | `scripts/update-internal-version-log.mjs` |
| 内部日志文件 | `CRM.Web/src/views/Debug/internal-version-log.txt` |
| 版本常量 | `CRM.Web/src/views/Debug/debugConstants.ts` → `export const FRONTEND_DEBUG_VERSION` |

**Windows 注意：** `git log` 的 `--format` 须拆成两次调用（`%ci` 与 `%s` 分开），避免 cmd 将 `%s` 误解析为环境变量。

**流程示意：**

```
git commit
    → post-commit 运行 update-internal-version-log.mjs
    → 写 txt + debugConstants.ts
    → git add + git commit --amend（SKIP_INTERNAL_VERSION_LOG=1）
    → post-commit 再次运行 → 检测首行已存在 → 退出
```

### 3.5 路由与权限

| 路由 | 组件 | `meta` | 导航守卫 |
|------|------|--------|----------|
| `/debug` | `DebugList.vue` | `requiresAuth: false` | `router/index.ts` 中 `isPublicPage` 免登录 |
| `/debug/internal-version-log` | `DebugInternalVersionLog.vue` | `requiresAuth: true`, `sysAdminOnly: true` | 未登录 → `/login`；非 sysAdmin → `/dashboard` |

`DebugList.vue` 版本面板提供链接：「版本更新日志」→ `/release-notes`；「内部版本日志」→ `/debug/internal-version-log`。

### 3.6 前端实现要点

- `DebugInternalVersionLog.vue` 通过 Vite `?raw` 导入 `internal-version-log.txt`，按行渲染 `<pre>`。
- 内部页与 Debug 子页（模拟数据、工具等）同属 `AppLayout` 子路由；主 `/debug` 虽在 layout 内但守卫层面对 `/debug` 路径单独放行免登录。

## 4. 外部版本日志

### 4.1 功能要求

1. 提供 **独立全页** `/release-notes`，免登录，渲染用户向更新说明。
2. 内容与右侧扩展面板「帮助」**共用同一 Markdown 源文件**（经 `help/menu-registry.json` 注册）。
3. 由产品/实施在发布前 **手工维护** 条目；**不**从 Git commit 自动同步。
4. 条目组织建议：按 **发布日期**（`## YYYY-MM-DD`）→ **功能模块**（`### 模块名`）→ bullet 说明。

### 4.2 编辑与同步

| 项 | 说明 |
|----|------|
| **源文件（唯一编辑入口）** | `help/pages/version/版本更新日志_MENU_RELEASE_NOTES.md` |
| **注册表** | `help/menu-registry.json` → `MENU_RELEASE_NOTES`，`docPath: "pages/version/版本更新日志_MENU_RELEASE_NOTES.md"`，`pathPrefixes: ["/release-notes"]` |
| **构建产物（勿手改）** | `CRM.Web/public/help/`（`.gitignore` 忽略，由同步脚本生成） |
| **同步命令** | `node scripts/sync-help.mjs`；或 `npm run dev` / `npm run build` 前自动执行（`CRM.Web/package.json` 的 `predev` / `prebuild`） |

### 4.3 页面与帮助集成

| 入口 | 行为 |
|------|------|
| `/release-notes` | `ReleaseNotesPage.vue`：`fetch(helpAssetUrl('pages/version/版本更新日志_MENU_RELEASE_NOTES.md'))`，`marked` 渲染 |
| 登录后访问带 help 面板的路由 | `HelpManualPanel.vue` 按 `helpDocPath.ts` 解析，打开同一路径 Markdown |
| `/debug` | 版本面板链接至 `/release-notes` |

`/release-notes` 为 **layout 外顶层路由**，与 `/login` 同级；守卫中与 Debug 主列表一并列入 `isPublicPage`。

### 4.4 对外 Markdown 编写建议

1. 首行可保留返回目录链接：`[帮助文档目录](../帮助文档目录.md)`（与其它 help 页一致）。
2. 一级标题：`# 版本更新日志`。
3. 每条发布用日期二级标题；其下按模块三级标题 + 用户可读 bullet（避免 commit hash、内部文件名）。
4. 不在此文写 post-commit、amend 等开发细节（见本文 §3）。

## 6. 发布与运维流程

### 6.1 日常开发

1. 正常 `git commit`；post-commit 自动更新内部日志并 amend。
2. 若需临时跳过：`SKIP_INTERNAL_VERSION_LOG=1 git commit ...`。
3. 本地/CI 构建前端时 `prebuild` 会将 `help/` 同步到 `public/help/`。

### 6.2 对用户发布说明

1. 编辑 `help/pages/version/版本更新日志_MENU_RELEASE_NOTES.md`，追加本次发布条目。
2. 执行 `node scripts/sync-help.mjs` 或走完整前端 build。
3. 部署后用户访问 `/release-notes` 或登录后在帮助面板查看。

### 6.3 部署核对

1. 打开线上 `/debug`（免登录）。
2. 对比 **当前前端构建版本** 与预期 commit 的 `1.1.{MMdd}-{HHmm} {subject}` 是否一致。
3. 需查完整内部历史时，以 sysAdmin 登录后打开 `/debug/internal-version-log`。

## 7. 与 Debug 页其它能力的关系

Debug 页除版本面板外，还包括数据库脱敏连接串、debug 表记录、以及需 sysAdmin 的子页（模拟数据、工具、AI 调试等）。版本日志 **不依赖后端 API**；内部日志纯前端静态文件，随前端构建打包发布。

详见 [Debug 页 PRD](../PRD/Debu页.md)、[AI 模块架构与实现](../System/AI模块架构与实现.md) §8。
