# 系统错误自动落库 — 设计与实现

**状态：** MVP 已实现  
**关联：** 用户反馈助手（独立，不自动写入 `user_feedback`）  
**权限脚本：** `scripts/ensure_sys_error_log_ops_postgresql.sql`  
**运维入口：** `/ops/system-errors`（运维 → 系统错误）  
**测试对照：** [系统错误自动落库-测试对照说明](../QA/系统/系统错误自动落库-测试对照说明.md)

---

## 1. 产品口径（已定稿）

| 项 | 定稿 |
|----|------|
| 记录范围 | **HTTP 500（未处理异常）** + **关键保存失败**（`DbUpdateException` / `DbUpdateConcurrencyException`） |
| 落库表 | 既有 `sys_error_log` |
| 运维入口 | **独立「系统错误」**，不挂到用户反馈台 |
| 用户侧 | Toast 业务友好文案 + **错误编号**（`E-{id}`）；不展示堆栈 |
| 与 AI 反馈 | 不自动建反馈单；用户可自愿反馈并粘贴错误编号 |

**不记：** 纯业务拒绝（校验、状态机、权限 403、404 等）。

---

## 2. 实现要点

| 组件 | 作用 |
|------|------|
| `ErrorHandlingMiddleware` | 未处理异常 → 写 `sys_error_log` → 500 + `errorId` |
| `PersistenceFailureErrorLogInterceptor` | `SaveChanges` 失败且为 DbUpdate* → 写日志（覆盖 Controller catch 包装场景） |
| `SysErrorIdResultFilter` | 若本请求已产生错误编号且响应为失败信封，附加 `errorId` / 文案中的「错误编号」 |
| `ErrorLogService` | 使用**独立 DI Scope / 新 DbContext** 写入，避免污染失败中的上下文 |
| `ErrorLogsController` | 运维分页查询 / 详情 / 标记已处理 |

错误编号格式：`E-{sys_error_log.Id}`（自增主键，无需额外列）。

---

## 3. 权限

| 权限码 | 说明 |
|--------|------|
| `sys.errorlog.read` | 查看系统错误列表与详情 |
| `sys.errorlog.resolve` | 标记已处理 |

默认授予 `SYS_ADMIN`。

侧栏 **「运维管理」整组仅系统管理员可见**。非管理员即使被授予本权限码，也看不到该菜单；直链/API 仍按上表校验。

---

## 4. 前端

- 菜单：运维管理 → 系统错误（仅系统管理员侧栏可见）  
- 列表规范对齐业务列表页  
- `getApiErrorMessage` / 拦截器：展示后端返回的 `errorId`

---

## 5. 上线步骤

2. 部署并重启 API
3. 管理员重新登录后验证菜单「运维 → 系统错误」
