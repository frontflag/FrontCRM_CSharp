## 一、定位

| 维度 | 说明 |
|------|------|
| 路由 | `/sales-order-items`，路由名 `SalesOrderItemList` |
| 统计粒度 | **销售明细行**（`sellorderitem`） |
| API 列表 | `GET /api/v1/sales-orders/items` |
| 数据权限 | `ApplySellOrderDataScopeAsync`（经主单 join） |
| 与主单列表 | 销售订单**主表**列表为另一页面，文案与字段独立 |

列表在分页查询后，对**当前页**行做 enrichment（扩展表进度、出库门闸、剩余可采、**采购员展示**等），与 `sellorderitemextend` 同步字段互补：后者存累计指标，前者存派生展示。

## 三、采购员列 — 设计需求

### 3.1 业务目标

在销售明细列表中，让销售/跟单人员快速看到「该行由哪些采购员在执行采购」，并支持按采购员筛选，无需进入采购订单明细列表。

### 3.2 已确认口径（定稿）

| 项 | 规则 |
|----|------|
| **数据来源** | **纯 PO 口径**：仅关联采购订单；**不回退**采购申请、报价、RFQ 分配采购员 |
| **关联链** | `sellorderitem.Id` ← `purchaseorderitem.sell_order_item_id` → `purchaseorder` 主表 |
| **采购员字段** | PO **主表** `PurchaseUserId`（非明细行字段） |
| **纳入 PO 明细** | `status ∉ {-1,-2}`（非审核失败/取消），且未软删（全局 query filter） |
| **纳入 PO 主表** | `status ≠ -2`（主表未取消） |
| **多人（1:N）** | 按 **PO 创建时间升序** 取采购员，再按 `PurchaseUserId` **去重**，登录账号用 **中文逗号 `，`** 拼接，如 `zhangsan，lisi` |
| **同 PO 多明细** | 同一主表采购员只贡献一次 |
| **展示内容** | 用户 **登录账号**（`User.UserName`，与采购申请列表 `purchaseUserAccount` 一致） |
| **无 PO** | 列显示 `—`（含仅有 PR、未下 PO 的行） |
| **脱敏** | 不受销售 521 脱敏影响；具备列表读权限即可见 |

### 3.3 未采用方案（记录）

| 方案 | 未采用原因 |
|------|------------|
| 创建/变更 PO 时回写销售明细冗余字段 | 1:N 拼接维护成本高，PO 取消/改人要全链路同步 |
| PR / 报价回退 | 产品定稿为「执行口径」，以已下 PO 为准 |
| 采购员级联下拉（`purchaseUserId`）首版 | 首版文本框即可，与采购订单明细列表一致 |

### 3.4 筛选需求

| 项 | 规则 |
|----|------|
| 控件 | **文本框**（首版），占位「采购员」 |
| 参数 | `purchaseUserAccount`（query string） |
| 匹配 | 模糊、不区分大小写；命中该行 **任一** 有效 PO 的采购员即保留 |
| 匹配字段 | 用户登录账号 `User.UserName`、用户姓名 `User.RealName`、PO 冗余 `PurchaseUserName` |
| 执行层 | **SQL 层** `EXISTS` 子查询（`SalesOrderItemLineListFilter`），保证分页 `totalCount` 正确 |
| 看板 | 与列表 **共用** `SellOrderItemLineQueryRequest` 与 `BuildItemListAnalyticsQueryRequestAsync` |

## 四、采购员列 — 实现方法

### 4.1 数据流

```
GET /api/v1/sales-orders/items
  → SalesOrderItemLineListQuery.GetPagedAsync        // 主查询 + 列表筛选（含 purchaseUserAccount）
  → SalesOrderService.EnrichSellOrderItemLineListAsync
       └── EnrichPurchaseUserAccountDisplayAsync    // 当前页批量拼 purchaseUserAccountDisplay
  → SalesOrdersController.MaskSellOrderLine          // 透出 purchaseUserAccountDisplay
```

**计算时机**：每次列表请求对**当前页** `SellOrderItemId` 批量查 PO 明细与主表 → 解析用户账号 → 内存分组拼接；**不落库**。

### 4.2 后端

| 模块 | 路径 | 职责 |
|------|------|------|
| 请求 | `SellOrderItemLineQueryRequest.PurchaseUserAccount` | `ISalesOrderService.cs` |
| 响应 | `SellOrderItemLineDto.PurchaseUserAccountDisplay` | 同上 |
| 列表筛选 | `SalesOrderItemLineListFilter.cs` | `EXISTS` PO 明细 + 主表 + `Users` |
| 展示 enrichment | `SalesOrderService.EnrichPurchaseUserAccountDisplayAsync` | 批量 `FindAsync` PO 行/主表 + `IUserService.GetByIdAsync` |
| 有效 PO 判定 | `PurchaseRequisitionPoLinkHelper.IsActivePoItem` / `IsActivePurchaseOrderHeader` | `CRM.Core/Utilities/` |
| 账号格式化 | `EntityLookupService.FormatUserLoginName` | 与采购申请列表一致 |
| 控制器 | `SalesOrdersController.GetSellOrderItemLines` | `[FromQuery] purchaseUserAccount`；匿名投影含 `PurchaseUserAccountDisplay` |

**筛选 SQL 概念**（EF 已落地）：

```text
sellorderitem 行保留，当 EXISTS (
  purchaseorderitem.sell_order_item_id = 行.Id
  AND 明细 status ∉ {-1,-2}
  JOIN purchaseorder ON 主表未取消
  AND (PO.PurchaseUserName ILIKE %kw%
       OR User.UserName / RealName ILIKE %kw%)
)
```

**展示拼接逻辑**（与筛选独立）：

1. 当前页 `lineIds` → 查关联 `PurchaseOrderItem`（有效明细）  
2. 关联 `PurchaseOrder`（未取消）→ 收集 `(CreateTime, PurchaseUserId)`  
3. 按销售行分组 → 按 `CreateTime` 排序 → `PurchaseUserId` 去重 → 查用户 → `Join("，", 账号)`

### 4.3 前端

| 模块 | 路径 |
|------|------|
| 列配置 | `buildSalesOrderItemListColumns.ts`（`salesUserName` 后插入 `purchaseUserAccountDisplay`） |
| 列表页 | `SalesOrderItemList.vue`（筛选框、`#col-purchaseUserAccountDisplay`、`loadList` / `boardFilters` 传参） |
| API 类型 | `salesOrder.ts` `getItemLines`、`salesOrderItemAnalytics.ts` |
| i18n | `salesOrderItemList.columns.purchaseUserAccount`、`filters.purchaseUserAccount`；销售员文案见 `columns.salesUser` |
| 列布局版本 | `column-layout-key="sales-order-item-list-v5"` |

### 4.4 性能说明

- 单页最多 100 行；enrichment 为 1 次 PO 明细批量查询 + 1 次 PO 主表 + 按去重用户 id 少量 `GetByIdAsync`，与既有 `PurchaseRemainingQty` enrichment 同级。  
- 筛选在 SQL 完成，避免「先分页再内存过滤」导致总数不准。
