# 收款核销 — 功能要求与实现说明

本文描述 **FrontCRM（CRM.Core / CRM.API / CRM.Web）** 中「收款核销」的业务口径、功能要求、数据模型与代码索引。与 [业务逻辑与数据关系文档](../业务逻辑与数据关系文档.md) §5.2.1、[财务 Phase 1 操作手册](../../EBS/财务/财务Phase1操作手册.md)、[收款记录帮助](../../help/pages/收款记录_MENU_FINANCE_RECEIPT.md) 交叉引用。

---

## 1. 业务定位

收款核销用于将 **已审核/已收款的客户来款**（收款单明细）或 **客户预收池余额**，与 **销售出库产生的应收款** 进行金额匹配，形成可追溯的核销流水。

| 概念 | 说明 |
|------|------|
| **应收款** | 销售出库单头完成后自动生成，一出库单对应一条 `finance_receivable` |
| **收款单明细** | 客户实际来款，审核通过后可参与核销 |
| **预收池** | 客户币别维度预收余额，可核销应收或由原收款明细余额转入 |
| **核销流水** | 每次匹配落库 `finance_receivable_write_off`，为审计与查询的唯一事实来源 |

**与旧版 EBS 差异**：本系统以 `finance_receivable` + `finance_receivable_write_off` 为核销主数据，不再使用独立的「核销单主表 + 核销明细表」模型。

**相关：** 销项发票与应收的 **开票匹配**（非现金核销）见 [销项发票核销-设计与实现](./销项发票核销-设计与实现.md)；桌面见 [销项发票核销桌面-设计与实现](./销项发票核销桌面-设计与实现.md)。

## 2. 功能要求

### 2.1 页面与入口

| 入口 | 路由 | 说明 |
|------|------|------|
| 收款核销工作台 | `/finance/receipt-write-off` | 三栏：待核销客户 → 待核销收款 → 待核销应收 |
| 收款核销流水 | `/finance/receipt-write-off/ledger` | 全量核销流水列表，支持关键字检索 |
| 应收款详情 | `/finance/receivables/:id` | 展示该应收的核销记录 |
| 销售订单明细详情 | 销售订单详情 → 双击明细行 → **收款核销** 页签 | 展示该销售明细关联的全部核销流水 |

菜单路径：**收款管理 → 收款核销**。

### 2.2 收款核销工作台（三栏交互）

1. **左栏 · 待核销客户**（读取逻辑见 §2.2.1、§2.2.2）
   - 后端 **始终** 返回存在 **待核销收款明细** 的客户（按客户 + 收款币别一行）；
   - 前端默认展示全部；可勾选 **「去除无待核销应收客户」** 仅保留同时有未清应收的行；
   - 无未清应收的行以 **灰色** 显示（勾选过滤后隐藏）；
   - 支持关键字搜索（客户中文名 / 英文名 / 客户编号 / 业务员账号）、双击或「选中」；
   - 展示 **待核销收款总额**（琥珀色，无应收时为灰）、**待核销收款条数**、收款日期范围；
   - **不入 API 结果** 的客户：仅有未清应收、或仅有预收池而无待核销收款。

### 2.2.1 左栏「待核销客户」— 读取逻辑（2026-07-05）

#### 总体结构

左栏数据分 **后端汇总** 与 **前端展示** 两层，职责如下：

| 层级 | 职责 | 说明 |
|------|------|------|
| **后端 API** | 确定「谁有待核销收款」 | 仅含待核销收款明细的客户；附带 `hasOpenReceivable` |
| **前端展示** | 过滤与样式 | 勾选项控制是否隐藏无应收行；灰显区分 |

左栏是 **来款侧入口**：财务人员在此找到「已登记来款、尚未分配完毕」的客户，再选中一行（含币别）进入中栏、右栏。

#### 一、后端：`GetWriteOffCustomerSummariesAsync`

**入口**：`GET /api/v1/finance/receivable-write-offs/customer-summaries?keyword=`  
**控制器**：`FinanceReceivableWriteOffsController.GetCustomerSummaries`  
**权限**：`finance-receipt.read`；`keyword` 可选。

**处理流水线**（与 `FinanceReceivableService.cs` 一致）：

| 步骤 | 方法 / 代码 | 说明 |
|------|-------------|------|
| 1 | `BuildPendingReceiptItemCandidatesAsync` | 扫描待核销收款明细候选（见下表） |
| 2 | 按 `customerId::currency` 聚合 | `BuildCustomerCurrencyKey`；累加 `pendingWriteOffTotal`、`pendingReceiptItemCount`；跟踪 `earliestReceiptDate` / `latestReceiptDate` |
| 3 | `GetPagedAsync(OnlyOpen=true, PageSize=2000, CurrentUserId)` | 查询当前用户可见的全部未清应收（`verified_to_be > 0`，含数据权限） |
| 4 | 构建 `openReceivableKeys` | 未清应收按 `customerId::currency` 去重为 HashSet |
| 5 | 映射 `FinanceWriteOffCustomerSummary` | 每行 `hasOpenReceivable = openReceivableKeys` 含该客户该币别 |
| 6 | `.Where(pendingReceiptItemCount > 0 && pendingWriteOffTotal > 0)` | 防御性过滤 |
| 7 | 排序 | 客户名 → 币别 |
| 8 | `EnrichWriteOffCustomerSummariesAsync` | 补全 `customerCode`、`customerEnglishName`、`salesUserName` 等 |
| 9 | `MatchesWriteOffCustomerKeyword` | 若传 `keyword`：匹配中文名、英文名、**客户编号**、业务员账号（忽略大小写） |

**`BuildPendingReceiptItemCandidatesAsync` 明细候选条件**：

| # | 条件 | 字段 / 说明 |
|---|------|-------------|
| 1 | 收款单未删除 | `finance_receipt.is_deleted = false` |
| 2 | 收款单状态 | **已审核(2)** 或 **已收款(3)** |
| 3 | 收款明细未删除 | `finance_receiptitem.is_deleted = false` |
| 4 | 明细剩余可核销 &gt; 0 | `FinanceReceiptItemWriteOffHelper.GetRemaining(item) > 0`（见 §3.2） |
| 5 | 历史主表无明细 | 已审核/已收款且 `receipt_amount > 0` 但无有效明细行时，**自动补落库一条明细** 后再参与扫描 |

**汇总维度**：`customer_id` + `receipt_currency`（同一客户多币别各占一行）。

**`hasOpenReceivable` 口径**（与右栏一致）：

- 该客户 + **收款币别** 维度，是否存在至少一条 **当前用户可见** 的未清应收（`verified_to_be > 0`，未软删）；
- 匹配键与左栏行相同：`customerId::currency`（应收 `currency` 须与左栏 `currency` 一致）；
- 使用与 `GetWriteOffCandidatesAsync` / 应收列表相同的 **应收数据权限**（`CurrentUserId` → `ApplyFinanceReceivableListDataScopeAsync`）。

**API 不返回**（不入左栏）的情形：

| 客户状态 | 是否出现在 API | 说明 |
|----------|----------------|------|
| 有待核销收款明细 | ✅ | 左栏数据源 |
| 仅有未清应收，无待核销收款 | ❌ | 在 **应收款列表** 跟进；来款审核后再入左栏 |
| 仅有预收池，无待核销收款 | ❌ | 不能仅凭预收池入列 |
| 收款单草稿/待审，或明细剩余为 0 | ❌ | 无可分配来款 |

> **历史变更**：2026-07-05 前左栏曾将未清应收计入 `pendingWriteOffTotal` 并允许「仅应收客户」入列（条数=0、总额&gt;0）。现 API **仅统计待核销收款**，应收仅通过 `hasOpenReceivable` 标记。

#### 二、左栏列字段（DTO）

| 界面列名 | DTO 字段 | 统计口径 |
|----------|----------|----------|
| 客户 / 业务员等 | `customerName` … `salesUserName` | enrich 后展示 |
| 待核销收款总额 | `pendingWriteOffTotal` | 该客户该币别待核销收款明细 **剩余可核销之和**（**不含**应收 `verified_to_be`） |
| 待核销收款条数 | `pendingReceiptItemCount` | 上述明细条数（≥ 1） |
| 收款日期 | `earliestReceiptDate` / `latestReceiptDate` | 所属收款单 `receipt_date` 最早/最近 |
| （不展示） | `hasOpenReceivable` | 是否有未清应收；驱动灰显与前端过滤 |

**响应模型** `FinanceWriteOffCustomerSummary`（`CRM.Core/Interfaces/IFinanceReceivableService.cs`）：

| 字段 | 类型 | 说明 |
|------|------|------|
| `customerId` | string | 客户 ID |
| `customerName` / `customerEnglishName` / `customerCode` | string? | 客户展示（enrich） |
| `salesUserId` / `salesUserName` | string? | 业务员 |
| `currency` | short? | 收款币别 |
| `pendingWriteOffTotal` | decimal | 待核销收款剩余合计 |
| `pendingReceiptItemCount` | int | 待核销收款明细条数 |
| `earliestReceiptDate` / `latestReceiptDate` | DateTime? | 收款日期范围 |
| `hasOpenReceivable` | bool | 该客户该币别是否存在未清应收 |

#### 三、前端：`FinanceReceiptWriteOffPage.vue`

| 项 | 实现 |
|----|------|
| 加载 | `loadCustomerSummaries()` → `financeReceivableApi.getWriteOffCustomerSummaries(keyword?)` → 写入 `customerSummaries` |
| 表格数据 | `displayedCustomerSummaries`（computed，见 §2.2.2） |
| 选中 | 双击 / 「选中」→ `loadCandidates(customerId, currency)`；`selectedCurrency` 取自左栏行币别 |
| 灰显 | `customerRowClassName`：`!hasOpenReceivable` → `is-write-off-customer-no-receivable` |
| 中栏 / 右栏币别 | `filteredReceiptItems`、`filteredReceivableRows` 按 `selectedCurrency` 过滤（与左栏行币别一致） |

选定客户后，**中栏 / 右栏** 由 `GetWriteOffCandidatesAsync(customerId)` 加载（待核销收款 + 待核销应收 + 预收池），与左栏入列规则独立。

### 2.2.2 左栏「去除无待核销应收客户」勾选项

**控件**：左栏搜索区，`excludeNoReceivable`（`el-checkbox`），i18n `financeReceiptWriteOff.excludeNoReceivable`，**默认不勾选**。  
**过滤位置**：**仅前端**；后端 API 不传此参数，始终返回完整待核销收款客户列表。

| 勾选项 | `displayedCustomerSummaries` | 右栏「待核销应收」 |
|--------|------------------------------|-------------------|
| **不勾选**（默认） | `customerSummaries` 全部 | 可能有数据，也可能为空（仅有来款、应收已结清或未出库） |
| **勾选** | `customerSummaries.filter(r => r.hasOpenReceivable)` | 选中行 **必有** 与该币别匹配的未清应收 |

**视觉区分**（不勾选时）：`hasOpenReceivable === false` 的行整行 **灰色**（含待核销收款总额列）；选中行仍保持黄色高亮。

**勾选后选中行处理**（`watch(excludeNoReceivable)`）：

- 若当前选中行被滤掉 → 自动选中过滤后第一行并 `loadCandidates`；若无行则 `clearCustomerSelection`。
- 刷新列表时（`loadCustomerSummaries`）：若已勾选且原选中行 `!hasOpenReceivable` → 清空选中。

**典型场景**：

| 场景 | 不勾选 | 勾选 |
|------|--------|------|
| 有待核销收款 + 有未清应收 | 正常色，可核销 | 显示，右栏有应收 |
| 有待核销收款 + 无未清应收（如来款余款待转预收） | **灰显**，右栏可能空 | **隐藏** |

2. **中栏 · 待核销收款**
   - 仅展示当前选中客户下、状态为 **已审核(2)** 或 **已收款(3)** 的收款单明细；
   - 可勾选一条或多条收款明细，展示可核销余额；
   - 未选客户时显示灰斜体占位提示。

3. **右栏 · 待核销应收**
   - 展示当前客户下 `verified_to_be > 0` 的应收款（经 `GetWriteOffCandidatesAsync` + 应收数据权限）；
   - 前端按左栏选中行的 **币别**（`selectedCurrency`）过滤展示，与 `hasOpenReceivable` 币别维度一致；
   - 「本次核销」列可录入本次分配金额（>0 时绿色加粗）；
   - 支持使用 **预收池** 分配（`advancePoolAllocations`）；
   - 提交前校验：至少一条分配金额 > 0。

4. **提交核销**
   - 一次提交可包含多条「收款明细 → 应收款」分配，以及多条「预收池 → 应收款」分配；
   - 若预收挂单销售单与应收销售单不一致，首次返回需用户确认的 SO 不匹配列表，确认后带 `confirmSoMismatch: true` 重提。

5. **收款余额转预收池**（可选操作）
   - 对仍有可核销余额的收款明细，可将余额转入客户预收池，便于后续纯预收核销。

6. **流水入口**
   - 页头按钮跳转「收款核销流水」页。

### 2.3 收款核销流水

- 数据来源：`finance_receivable_write_off` 关联 `finance_receivable`（及可选 `finance_receipt`）；
- 列：核销时间、来源、收款单号、应收款号、出库单号、销售订单号、客户、PN、品牌、核销金额、操作人、备注；
- 应用应收款 **数据权限**（与应收款列表一致）；
- 支持按关键字过滤（应收号、出库号、销售单号、客户、PN、收款单号等）。

### 2.4 销售订单明细「收款核销」页签

- 页签名称：**收款核销**（原「收款」页签已替换）；
- 内容：该 `sell_order_item_id` 下所有核销流水（与流水页字段一致，无分页，上限 2000 条）；
- 数据接口：`GET .../sell-order-items/{id}/detail-tab-aggregates` 返回字段 `receiptWriteOffs`。

### 2.5 权限

| 操作 | RBAC |
|------|------|
| 查看核销候选、流水、客户汇总 | `finance-receipt.read` |
| 执行核销、余额转预收池 | `finance-receipt.write` |
| 应收款列表/详情（核销对象） | 应收款数据权限 + 财务读权限 |

## 3. 核心业务规则

### 3.1 应收款生成（核销前置）

- 触发：销售出库单状态为 **出库完成(4)**，且类型为销售出库（`StockOutTypeCode.IsSalesStockOut`）；
- 服务：`FinanceReceivableService.TryEnsureFromStockOutAsync`；
- 金额：`stock_out.total_amount`，若为 0 则 `total_quantity × sell_order_item.price`；
- 初始：`verified_done = 0`，`verified_to_be = amount`，`verification_status = 待核销`；
- 同一 `stock_out_id` 仅一条有效应收（软删除外）。

### 3.2 可核销余额口径

| 对象 | 可核销余额计算 |
|------|----------------|
| 收款明细 | `receipt_convert_amount - verified_amount - advance_pool_amount` |
| 应收款 | `verified_to_be` |
| 预收池 | 客户 + 币别维度 `finance_customer_advance` 余额 |

**左栏汇总**（§2.2.1）仅使用 **收款明细可核销余额** 聚合，不使用应收 `verified_to_be`。

### 3.3 核销提交校验（`ApplyWriteOffAsync`）

1. 至少一条有效分配（收款明细或预收池）；
2. 同一批次不可跨 **多个客户**；
3. 使用收款明细时：收款单须 **已审核或已收款**；收款币别须与应收币别一致；
4. 每条分配：金额 > 0，且 ≤ 对应收款明细/应收剩余可核销额；
5. 预收池分配总额 ≤ 客户该币别预收余额；
6. SO 不匹配时须 `confirmSoMismatch`（见 §3.5）。

### 3.4 核销落库与回写

每笔成功分配：

1. 写入 `finance_receivable_write_off`（`write_off_source`：10=收款明细，20=预收池）；
2. 累加 `finance_receipt_item.verified_amount`（来源为收款明细时）；
3. 累加 `finance_receivable.verified_done`，重算 `verified_to_be` 与 `verification_status`；
4. 预收池来源时 additionally 调用 `FinanceCustomerAdvanceService.ApplyFromPoolAsync`；
5. 对涉及的 `sell_order_item_id` 调用 `SellOrderItemExtendSyncService.RecalculateAsync`。

### 3.5 预收与销售单不匹配确认

当收款明细的预收挂单 `advance_sell_order_id`（或 `sell_order_id`）与应收款的 `sell_order_id` 不一致，或预收池核销指定了不同的 `advanceSellOrderId` 时，收集 `soMismatches` 列表。用户确认后继续核销，备注可记「SO不匹配已确认」。

### 3.6 销售明细「收款状态」与单条应收核销的关系（重要）

以下两个指标 **不可混用**：

| 展示位置 | 口径 | 完成条件 |
|----------|------|----------|
| **应收款详情** | 单条 `finance_receivable` | `verified_to_be = 0` → 该出库批次应收已核销完毕 |
| **销售订单明细 · 收款状态** | 整行 `sellorderitemextend` | `receipt_amount_finish`（该行所有应收 `verified_done` 之和）相对 **销售行全额** `qty × price` |

因此：**一条应收款全部核销 ≠ 销售明细收款完成**。一条销售明细可多次出库、产生多条应收；仅当累计已核销金额达到销售行全额时，`ReceiptProgressStatus` 才为「收款完成(2)」。

实现：`SellOrderItemExtendSyncService` 中 `ReceiptAmount = lineQty × price`，`ReceiptAmountFinish = Σ receivable.verified_done`。

## 4. 数据模型

### 4.1 主表

| 表 | 说明 |
|----|------|
| `finance_receivable` | 应收款（出库批次） |
| `finance_receivable_write_off` | 核销流水（审计主表） |
| `finance_receipt` / `finance_receipt_item` | 收款单及明细 |
| `finance_customer_advance` / `finance_customer_advance_ledger` | 预收池及台账 |

### 4.2 核销流水关键字段

| 字段 | 说明 |
|------|------|
| `finance_receivable_id` | 必填，关联应收 |
| `finance_receipt_id` / `finance_receipt_item_id` | 来源为收款明细时填写 |
| `write_off_source` | 10 收款明细；20 预收池 |
| `amount` | 本次核销金额 |
| `operator_user_id` | 操作人 |
| `create_time` | 核销时间 |
| `is_deleted` | 软删；反核销后为 true，默认查询排除 |

### 4.3 编码

应收款流水号：模块码 `FinanceReceivable`，前缀 `ARV`（如 `ARV0000A`）。

## 5. API 契约

控制器：`FinanceReceivableWriteOffsController`（`/api/v1/finance/receivable-write-offs`）

## 7. 典型业务场景

### 7.1 单次出库、一次收款、一次核销

出库完成 → 生成应收 ARV → 客户来款录入收款单并审核 → 收款核销页选定客户 → 勾选收款明细与应收 → 填写本次核销金额 → 提交。应收详情显示「已核销」；若销售行仅此一批出库且金额等于行全额，则销售明细收款状态为「收款完成」。

### 7.2 分批出库、分次核销

同一销售明细多次出库 → 多条应收。可对同一收款单分多次核销到不同应收，或多次收款分别核销。销售明细收款状态按 **行全额** 与 **累计 verified_done** 计算，在全部出库应收均核销且累计达到行全额前，显示「部分收款」。

### 7.3 预收池核销

客户 **已在左栏选中**（即存在待核销收款）时，右栏仍展示该客户预收池余额，可对右侧应收填写预收分配并提交；流水 `write_off_source = 20`，无收款单号。

**注意**：若客户 **仅有预收池、无任何待核销收款明细**，则 **不会出现在左栏 API**；须先登记来款。若 **有待核销收款但无未清应收**（灰显行），可将余款 **转预收池** 或等待新出库生成应收。

### 7.4 仅有应收、尚未来款

客户已出库、应收 `verified_to_be &gt; 0`，但尚未录入/审核收款单 → **不在左栏 API**。业务在 **应收款** 模块跟进；来款到达并审核后，客户进入左栏；勾选「去除无待核销应收客户」时右栏必有应收。

### 7.5 仅有来款、尚无未清应收（灰显行）

客户已审核来款、明细仍有剩余，但对应币别 **无未清应收**（如应收已全部核销、或尚未出库）→ 出现在左栏 API 且 **灰显**；不勾选时可选中，右栏应收可能为空，可 **转预收池**；勾选「去除无待核销应收客户」后 **隐藏**。

### 7.6 查询与追溯

- 财务：核销流水页按客户/单号检索；
- 业务：销售订单 → 明细详情 → 收款核销页签查看该 PN 行全部核销记录；
- 财务：应收款详情查看针对该出库批次的核销明细。

## 8. 测试与回归要点

1. 核销后 `finance_receivable_write_off` 行数与金额正确；
2. 收款明细 `verified_amount`、应收 `verified_done/verified_to_be` 同步；
3. 销售明细 `ReceiptProgressStatus` 在部分/全部核销场景下符合 §3.6 口径；
4. SO 不匹配时首次返回 `requiresSoMismatchConfirm`，确认后可成功；
5. 无 `finance-receipt.write` 时 POST 核销 403；
6. 销售明细页签 `receiptWriteOffs` 与流水页同源数据一致；
7. **左栏客户汇总（§2.2.1）**：`customer-summaries` 仅含待核销收款客户；`pendingReceiptItemCount ≥ 1`；`pendingWriteOffTotal` 等于收款剩余合计；`hasOpenReceivable` 与右栏未清应收（同币别、同数据权限）一致。
8. **去除无待核销应收客户（§2.2.2）**：勾选后左栏仅 `hasOpenReceivable === true` 的行；取消勾选后灰显行重新出现；勾选时选中灰显行应自动切换或清空。
9. 仅有未清应收 / 仅预收池客户 **不出现在** `customer-summaries`。

## 9. 反核销（与正向核销对称）

当收款单已在工作台完成核销、管理员需强制删除纠错时，须先 **收款反核销** 撤销本单全部「收款明细 → 应收」匹配，再执行 `force-delete`。

| 项 | 说明 |
|----|------|
| 与正向关系 | 软删 `finance_receivable_write_off`（source=10）、回滚应收 `verified_*`、明细 `VerifiedAmount`；主单 **Status 不变**（2/3） |
| 与「反审核」 | **不是**反审核；不将已收款打回已审核 |
| 预收池 | `AdvancePoolAmount>0` 时须先处理预收池，反核销会拒绝 |
