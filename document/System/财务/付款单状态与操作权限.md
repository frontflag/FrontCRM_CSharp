# 付款单状态与操作权限

本文描述 **FrontCRM（CRM.Core / CRM.API / CRM.Web）** 中付款单（`FinancePayment`）的状态枚举、业务操作边界、权限与 API/前端实现索引。与 [财务 Phase 1 状态流转矩阵](../../PRD/辅助功能/财务Phase1状态流转矩阵.md)、[权限-财务](../权限/权限-财务.md)、[请款 PRD](../../PRD/业务功能/财务/请款PRD.md) 交叉引用。

---

## 1. 核心设计原则

**请款（request）与付款执行（execution）是两类独立业务操作**，不得混在同一编辑表单中：

| 操作类型 | 业务含义 | 典型字段 | 允许状态 |
|----------|----------|----------|----------|
| **编辑请款** | 修改申请内容（供应商账户、费用、明细请款额等） | `vendorBankId`、`paymentMode`、`paymentCurrency`、费用字段、`requestRemark`、明细 `paymentAmountToBe` / `lineRemark` | `1` 新建、` -1` 审核失败 |
| **付款执行** | 财务实际打款信息（含执行阶段费用微调） | `companyBankId`、`paymentDate`、`bankSlipNo`、水单附件；**费用六字段**（见 §6.1） | `10` 审核通过 |
| **撤回** | 审核通过后退回草稿，清空执行信息 | 清 `companyBankId`、`bankSlipNo`、`paymentDate`、`paymentUserId`；软删 `FINANCE_PAYMENT` 附件 | `10` → `1` |
| **状态动作** | 提交/审批/完成/取消 | 仅改 `Status` 及审批相关字段 | 见 §2 |

编辑请款 **不可增删 PO 明细行**；驳回单（`-1`）与同 PO 行上的新建请款（`1`）可并存。

## 2. 状态枚举（`FinancePayment.Status`）

| 值 | 常量含义 | 说明 |
|----|----------|------|
| `1` | 新建 | 草稿，可编辑请款、提交审核、取消 |
| `2` | 待审核 | 审批中；不可编辑请款；可取消 |
| `10` | 审核通过 | 可保存付款执行、确认完成、撤回 |
| `100` | 付款完成 | 终态，无写操作 |
| `-1` | 审核失败 | 可编辑请款（保存后自动 `-1→1`）、取消 |
| `-2` | 取消 | 终态 |

### 2.1 状态流转

```
                    提交审核(1→2)
         ┌──────────────────────────────┐
         │                              ▼
    ┌────┴────┐   审批通过(2→10)   ┌──────────┐   完成(10→100)   ┌──────────┐
    │ 新建(1) │ ◄──────────────── │ 待审核(2) │ ──────────────► │审核通过(10)│ ──► 付款完成(100)
    └────┬────┘                   └────┬─────┘                   └─────┬────┘
         │                             │ 驳回(2→-1)                      │
         │                             ▼                                 │ 撤回(10→1)
         │                        ┌──────────┐                           │
         └──── 编辑保存(-1→1) ◄───│审核失败(-1)│                           │
                                  └──────────┘                           │
                                                                         └──► 清空执行字段后回到新建(1)

取消：1 或 2 → -2
反核销：100 → 10（回滚付款明细核销并同步采购付款状态；须输入付款单号确认）
```

**与旧版 EBS 差异**：审核失败为 `-1`（非 `-2`）；付款完成为 `100`（非 `20`）；取消为 `-2`。

**软删除：** 普通/强制删除将主表与明细标 `is_deleted`。默认付款记录列表**不展示**已删除单；**按付款单号筛选**时包含已删除行（状态旁「已删除」），详情只读。删除后须同步采购明细 `FinancePaymentStatus`（无未删除付款明细则回到未付款），避免「付款完成」却列表查不到。

**反核销与强制删除**：付款完成且已核销时，须先执行 **反核销**（`POST .../reverse-verification`），再由系统管理员 **强制删除**（`POST .../force-delete`）。普通删除（`DELETE`）与强制删除共用同一核销守卫。

> 付款/收款反核销的完整设计对照与实现索引见 [付款收款反核销-设计与实现](./付款收款反核销-设计与实现.md)。

## 3. 状态 × 操作矩阵

| 状态 | 编辑请款 | 提交审核 | 撤回 | 保存/完成付款执行 | 反核销 | 取消 |
|------|:--------:|:--------:|:----:|:-----------------:|:------:|:----:|
| `1` 新建 | ✅ | ✅ | — | — | — | ✅ |
| `-1` 审核失败 | ✅（保存后 → `1`） | ✅（需先回到 `1` 再提交） | — | — | — | ✅ |
| `2` 待审核 | ❌ | — | — | — | — | ✅ |
| `10` 审核通过 | ❌ | — | ✅ | ✅ | — | ❌ |
| `100` 付款完成 | ❌ | — | — | — | ✅ | ❌ |
| `-2` 取消 | ❌ | — | — | — | — | ❌ |

前端按钮显隐与上表一致；服务端在 `FinancePaymentService` 中二次校验，防止越权改状态。

## 4. 权限模型

### 4.1 RBAC 功能码

| 操作 | 所需权限 | 部门只读 |
|------|----------|----------|
| 编辑请款 | `purchase-order.write` **或** `finance-payment.write` | 财务部 `FinanceDataAccess=1` 时，**编辑请款 API 对持有 `purchase-order.write` 的用户放行**（`allowPurchaseOrderWriteBypass`） |
| 提交审核（设计） | 同上 | 同上 |
| 撤回 | **创建人**（`CreateByUserId === 当前用户`）**或** `finance-payment.write` | 仅财务写用户检查 `FinanceDataAccess`；创建人撤回不依赖 PO 写权限 |
| 保存付款执行 / 完成 | `finance-payment.write` | 财务部须非只读 |
| 反核销 | `finance-payment.write` | 财务部须非只读；须输入付款单号确认 |
| 取消 / 删除 | `finance-payment.write` | 财务部须非只读；已核销须先反核销 |
| 列表/详情查看 | `finance-payment.read` **或** `purchase-order.read` | — |

### 4.2 前端写门控（Composable）

| Composable | 路径 | 逻辑 |
|------------|------|------|
| `useFinanceWriteGate()` | `CRM.Web/src/composables/useDepartmentDataReadOnly.ts` | `finance-payment.write` + 身份未剥离 + 主部门财务数据非只读 |
| `usePurchaseOrderWriteGate()` | 同上 | `purchase-order.write` + 主部门采购数据非只读 |

列表/详情/PO Tab 中：

- `canEditRequest` / `canSubmitAudit`：`canFinancePaymentWrite \|\| canWritePo`，且 `status ∈ {1, -1}`（提交仅 `status === 1`）
- `canPayExecute`：`canFinancePaymentWrite && status === 10`
- `canReverseVerification`：`canFinancePaymentWrite && status === 100`
- `canWithdraw`：`status === 10 && (canFinancePaymentWrite \|\| 当前用户为创建人)`

## 5. 编辑请款：字段与校验

### 5.1 可编辑字段（主表 + 明细）

**主表**：`vendorBankId`、`paymentMode`、`paymentCurrency`、`requestRemark`、`feeIntermediateBank`、`feeBankCharge`、`feeFreight`、`feeMisc`、`feeRounding`、`feeIntermediateBankPayer`

**明细**（行数固定）：`paymentAmountToBe`、`lineRemark`

**不可编辑**：PO 明细关联（不可增删行）、付款执行字段、状态、编号等。

### 5.2 金额计算

```
PaymentAmountToBe = Σ(明细.PaymentAmountToBe) + Σ(费用字段)
```

服务端在 `UpdateRequestAsync` 中重算，不信任客户端合计。

### 5.3 明细请款上限

对每条 PO 明细：

```
maxAllowed = lineTotal(Qty × Cost) - otherValidRequested
```

其中 `otherValidRequested` 为**同一 PO 行**上、**其他有效付款单**（非取消、非审核失败、非当前单）的请款额之和。  
实现：`FinancePaymentService.GetMaxRequestAmountForPoLineAsync` / `ValidateAndApplyRequestItemsAsync`。

### 5.4 驳回后保存

`UpdateRequestAsync` 在 `status === -1` 时保存成功后自动置 `status = 1`，便于再次提交审核。

## 6. 付款执行与撤回

### 6.1 付款执行（`UpdateExecutionAsync`）

- 仅 `status === 10`（`100` 付款完成后不可再改费用）
- **付款执行字段**：`companyBankId`、`paymentDate`、`bankSlipNo`（及对话框内水单附件上传）
- **费用字段**（与请款相同六格，执行阶段可编辑；**不改明细行** `paymentAmountToBe`）：
  - `feeIntermediateBank`、`feeBankCharge`、`feeFreight`、`feeMisc`、`feeRounding`
  - `feeIntermediateBankPayer`（文案：**费用承担方**，取值 `我方` / `供应商`）
- **校验**：各费用金额 `≥ 0`（与请款一致）
- **金额重算**（保存 execution 时服务端执行，不信任客户端合计）：

```
PaymentAmountToBe = Σ(明细.PaymentAmountToBe) + Σ(费用字段)
```

- 撤回（`10 → 1`）后费用**保留**在请款单上；若需调整，在请款阶段（`UpdateRequestAsync`）再次编辑

UI：`FinancePaymentPayDialog.vue` — 布局为 **收款信息 → 费用明细 → 付款信息**；请款明细与主表请款字段只读，保存走 `PUT .../execution` 并提交费用六字段。付款金额随费用实时合计展示。

详情：`FinancePaymentDetail.vue` — 费用以六字段只读网格展示（与请款布局一致）；待付款态展示 `paymentAmountToBe`。

- 确认完成：`POST .../complete` → `10 → 100`，回写 PO 明细核销

### 6.2 撤回（`WithdrawAsync`）

- 仅 `status === 10`
- 权限：创建人或 `finance-payment.write`（后者须通过财务只读校验）
- 效果：
  - `10 → 1`
  - 清空 `CompanyBankId`、`BankSlipNo`、`PaymentDate`、`PaymentUserId`
  - 软删除业务类型 `FINANCE_PAYMENT` 的附件
- 用户需重新编辑请款并提交审批

## 7. API 端点映射

| 操作 | 方法 | 路径 | 控制器权限 |
|------|------|------|------------|
| 编辑请款 | PUT | `/api/v1/finance/payments/{id}/request` | `RequireAny`: `finance-payment.write`, `purchase-order.write` |
| 保存付款执行 | PUT | `/api/v1/finance/payments/{id}/execution` | `finance-payment.write` |
| 撤回 | POST | `/api/v1/finance/payments/{id}/withdraw` | 登录 + 服务层创建人/财务写校验 |
| 提交审核 | POST | `/api/v1/finance/payments/{id}/submit` | `finance-payment.write`（见 §7.1） |
| 通用改状态 | PATCH | `/api/v1/finance/payments/{id}/status` | `RequireAny`: 财务写 / PO 写 |
| 审核通过/驳回 | POST | `.../approve`, `.../reject` | `finance-payment.write` |
| 付款完成 | POST | `.../complete` | `finance-payment.write` |
| 反核销 | POST | `.../reverse-verification` | `finance-payment.write` |
| 取消 | POST | `.../cancel` | `finance-payment.write` |

DTO：`CRM.Core/Interfaces/IFinancePaymentService.cs`  
- `UpdateFinancePaymentRequestBody` / `UpdateFinancePaymentItemRequest`  
- `UpdateFinancePaymentExecutionRequest`

### 7.1 已知实现差异（提交审核）

**设计**上提交审核与编辑请款权限相同（PO 写或财务写）。  
**当前** `POST .../submit` 仍标注为仅 `finance-payment.write`；采购员侧若需提交，应使用 `PATCH .../status`（`1→2`）或后续对齐 `Submit` 端点权限。前端列表对 PO 写用户展示「提交审核」按钮时需注意该差异。
