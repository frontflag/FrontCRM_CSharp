# 付款与收款反核销 — 设计要件与实现说明

本文描述 **FrontCRM（CRM.Core / CRM.API / CRM.Web）** 中付款单、收款单的 **反核销**（`reverse-verification`）业务口径、设计决策、数据回滚与代码索引。

与 [付款单状态与操作权限](./付款单状态与操作权限.md)、[收款核销-设计与实现](./收款核销-设计与实现.md)、[强制删除 API 契约与错误码](../../实现方案/强制删除_API契约与错误码.md) 交叉引用。

---

## 1. 术语说明（重要）

| 口语/误称 | 正确术语 | 含义 |
|-----------|----------|------|
| 反审核 | **反核销** | 撤销「资金已匹配到下游应付/应收」的记账结果 |
| 撤回请款 / 撤回审核 | **撤回**（付款 `withdraw`） | 审核通过(10) 退回新建(1)，清空执行字段；**与反核销无关** |
| 取消收款单 | **取消**（`status→4`） | 作废单据；**与反核销无关** |

**反核销 ≠ 反审核**：不将单据从「已审核/已收款」打回「待审/草稿」，除非付款侧因业务耦合必须回滚主单状态（见 §3.1）。

---

## 2. 业务背景：为何需要反核销？

财务单据在 **已发生核销** 后，强制删除（`force-delete`）会被守卫拦截，提示存在下游业务节点。管理员纠错的标准路径为：

```text
已核销的单据
  → ① 反核销（清除核销下游）
  → ② 强制删除（SYS_ADMIN + 确认单号）
```

普通 `DELETE` 与 `force-delete` **共用同一核销守卫**（付款、收款均已对齐）。

## 3. 付款反核销

### 3.1 设计要件

| 维度 | 要求 |
|------|------|
| **触发场景** | 付款单 `Status=100`（付款完成）且明细已核销；需强制删除或重新处理付款 |
| **粒度** | **整单**反核销（不支持按明细选择性撤销） |
| **主单状态** | **必须回滚** `100 → 10`（审核通过）。付款完成与核销强耦合：完成即自动核销全部明细 |
| **主单金额** | `PaymentAmount`、`PaymentTotalAmount` 归零 |
| **明细回滚** | 全部 `FinancePaymentItem`：`VerificationStatus=0`，`VerificationDone=0`，`VerificationToBe=PaymentAmountToBe`，`PaymentAmount=0` |
| **下游同步** | 按明细关联的 `PurchaseOrderItemId` 调用 `SyncPurchaseFinanceStatusAsync`，重算 PO 明细/主单付款状态 |
| **审计** | `log_operation`，`ActionType=付款反核销`；摘要含关联采购明细单号（最多 5 个） |
| **独立核销流水表** | 无；核销状态仅存于付款明细字段 |

#### 正向核销（反核销的对称操作）

「确认付款完成」`UpdateStatusAsync(100)` 时 **自动** 将本单全部明细标为核销完成：

- `VerificationDone = PaymentAmountToBe`
- `VerificationToBe = 0`
- `VerificationStatus = 2`
- `PaymentAmount = PaymentAmountToBe`

随后同步采购付款状态。因此反核销必须同时回滚主单状态，否则会出现「主单仍显示付款完成、明细却无核销」的矛盾。

### 3.2 前置条件

| # | 规则 |
|---|------|
| P1 | 付款单存在 |
| P2 | `confirmBillCode` 与 `FinancePaymentCode` 完全一致 |
| P3 | `Status = 100` |
| P4 | 至少一条明细 `VerificationStatus > 0` 或 `VerificationDone > 0` |
| P5 | 财务数据可写（非只读） |

### 3.3 API 与权限

| 项 | 值 |
|----|-----|
| 方法 | `POST /api/v1/finance/payments/{id}/reverse-verification` |
| Body | `{ "confirmBillCode": "PAY00xxx" }` |
| 权限 | `finance-payment.write`（**不要求** SYS_ADMIN） |
| 成功 | 200，`data` 为回滚后的 `FinancePayment` |
| 典型错误 | 400 单号不匹配/无需反核销；409 非付款完成状态 |

### 3.4 强制删除守卫

`IForceDeleteGuardService.CanForceDeleteFinancePaymentAsync`：本单任一 `FinancePaymentItem` 满足 `VerificationStatus > 0` **或** `VerificationDone > 0` → 拒绝。

拦截文案示例：`存在下游业务节点：付款核销明细；下游数据单号：{PO明细号}`

### 3.5 实现索引

| 层级 | 路径 |
|------|------|
| 接口 | `IFinancePaymentService.ReverseVerificationAsync` |
| 服务 | `CRM.Core/Services/FinancePaymentService.cs` → `ReverseVerificationAsync` |
| 守卫 | `ForceDeleteGuardService.CanForceDeleteFinancePaymentAsync` |
| 控制器 | `FinancePaymentsController` → `POST {id}/reverse-verification` |
| 操作日志常量 | `OperationLogActionTypes.FinancePaymentReverseVerification` |
| 前端 API | `financePaymentApi.reverseVerification` |
| 前端入口 | `FinancePaymentList.vue`、`FinancePaymentDetail.vue`（`status===100`） |
| 单元测试 | `FinanceFlowServiceTests.ReverseVerificationAsync_*` |

## 4. 收款反核销

### 4.1 设计要件

| 维度 | 要求 |
|------|------|
| **触发场景** | 收款单已在核销工作台（或遗留 API）完成核销；需强制删除或重新核销 |
| **粒度** | **整单**反核销 |
| **主单状态** | **不回滚**（已确认 D1-A）：`Status` 保持 `2`（已审核）或 `3`（已收款）。来款确认与应收核销解耦 |
| **主单金额** | `ReceiptAmount`、`ReceiptDate` 等不变 |
| **明细回滚** | `VerifiedAmount` 归零，`VerificationStatus` 按余额重算 |
| **核销流水** | 物理删除本单关联的 `finance_receivable_write_off`（`write_off_source=10`）；完整摘要写入操作日志 |
| **应收回滚** | 每条流水对应 `FinanceReceivable`：`VerifiedDone` 减、`VerifiedToBe` 重算、`VerificationStatus` 重算 |
| **遗留路径** | 无 write_off 但 `VerifiedAmount>0`（旧 `VerifyReceiptItemAsync`）：按 `FinanceSellInvoiceId` 回滚销项发票 `ReceiveDone/ReceiveToBe` |
| **下游同步** | `SellOrderItemExtendSync.RecalculateAsync`；`SyncSellOrderReceiptStatusAsync` 重算销售订单头 `FinanceReceiptStatus` |
| **预收池** | `AdvancePoolAmount > 0` 时 **拒绝反核销**；须先回滚预收池（二期「反预收入账」） |

#### 正向核销（反核销的对称操作）

主路径：`FinanceReceivableService.ApplyWriteOffAsync` → `ApplyReceivableWriteOffCoreAsync`

- 写 `finance_receivable_write_off`
- 增加收款明细 `VerifiedAmount`、应收 `VerifiedDone`
- 重算销售行收款进度

收款单标记「已收款(3)**不自动核销**；核销在状态 2 或 3 下通过工作台独立提交。

### 4.2 前置条件

| # | 规则 |
|---|------|
| P1 | 收款单存在且未软删 |
| P2 | `confirmBillCode` 与 `FinanceReceiptCode` 完全一致 |
| P3 | `Status ∈ {2 已审核, 3 已收款}` |
| P4 | 存在可撤销核销：明细 `VerificationStatus>0` 或 `VerifiedAmount>0`，或存在 ReceiptItem 来源 write_off |
| P5 | 无明细 `AdvancePoolAmount > 0` |
| P6 | 财务数据可写 |

### 4.3 API 与权限

| 项 | 值 |
|----|-----|
| 方法 | `POST /api/v1/finance/receipts/{id}/reverse-verification` |
| Body | `{ "confirmBillCode": "REC00xxx" }` |
| 权限 | `finance-receipt.write`（**不要求** SYS_ADMIN） |
| 成功 | 200，`data` 为回滚后的 `FinanceReceipt` |
| 典型错误 | 400 单号不匹配/无需反核销/存在预收池；409 状态不允许 |

### 4.4 强制删除守卫

`IForceDeleteGuardService.CanForceDeleteFinanceReceiptAsync` 在以下任一条件拒绝：

| 条件 | 拦截方向 |
|------|----------|
| 明细 `VerificationStatus > 0` 或 `VerifiedAmount > 0` | 收款核销明细 / 销项发票单号 |
| 明细 `AdvancePoolAmount > 0` | 客户预收池入账 |

### 4.5 实现索引

| 层级 | 路径 |
|------|------|
| 编排接口 | `IFinanceReceiptService.ReverseVerificationAsync` |
| 编排服务 | `CRM.Core/Services/FinanceReceiptService.cs` → `ReverseVerificationAsync`、`ReverseLegacySellInvoiceVerificationAsync` |
| 流水回滚 | `IFinanceReceivableService.ReverseWriteOffsByReceiptAsync` |
| 流水服务 | `CRM.Core/Services/FinanceReceivableService.cs` → `ReverseWriteOffsByReceiptAsync` |
| 守卫 | `ForceDeleteGuardService.CanForceDeleteFinanceReceiptAsync` |
| 控制器 | `FinanceReceiptsController` → `POST {id}/reverse-verification` |
| 操作日志常量 | `OperationLogActionTypes.FinanceReceiptReverseVerification` |
| 前端 API | `financeReceiptApi.reverseVerification` |
| 前端入口 | `FinanceReceiptList.vue`、`FinanceReceiptDetail.vue`（`status∈{2,3}`） |
| 单元测试 | `FinanceFlowServiceTests.ReverseVerificationAsync_WhenStatus3_*`、`CanForceDeleteFinanceReceiptAsync_*` |

## 5. 付款 vs 收款对照总表

| 维度 | 付款 | 收款 |
|------|------|------|
| **产品名称** | 反核销 | 反核销 |
| **允许主单状态** | 仅 `100` 付款完成 | `2` 已审核 或 `3` 已收款 |
| **反核销后主单状态** | `100 → 10` | **不变**（2 或 3） |
| **核销如何产生** | 付款完成时 **自动** | 工作台 **手动** 提交（或遗留 API） |
| **核销审计表** | 无 | `finance_receivable_write_off` |
| **反核销是否删流水** | — | 物理删除 write_off 行 |
| **核心下游** | 采购订单明细付款状态 | 应收款 + 销售订单收款进度 |
| **额外下游** | — | 销项发票（遗留路径）、预收池入账（拦截） |
| **确认方式** | 输入付款单号 | 输入收款单号 |
| **写权限** | `finance-payment.write` | `finance-receipt.write` |
| **强删权限** | `finance-payment.write` + SYS_ADMIN | `finance-receipt.write` + SYS_ADMIN |

## 6. 端到端流程（管理员纠错）

### 6.1 付款

```text
PAY00xxx  Status=100  明细已核销
    │
    ├─ POST .../payments/{id}/reverse-verification  { confirmBillCode }
    │     → Status=10，明细核销清零，PO 付款状态回滚
    │
    └─ POST .../payments/{id}/force-delete  { confirmBillCode }  [SYS_ADMIN]
          → 软删付款单及明细
```

### 6.2 收款

```text
REC00xxx  Status=2|3  明细已核销（或存在 write_off）
    │
    ├─ [若 AdvancePoolAmount>0] 须先处理预收池（当前无自动回滚 API）
    │
    ├─ POST .../receipts/{id}/reverse-verification  { confirmBillCode }
    │     → Status 不变，核销/流水/应收回滚，销售收款状态回滚
    │
    └─ POST .../receipts/{id}/force-delete  { confirmBillCode }  [SYS_ADMIN]
          → 软删收款单及明细
```

## 7. 前端交互规范

与付款对齐：

1. 列表操作列、详情页头展示 **「反核销」**（warning 色）。
2. `window.prompt` 要求用户 **完整输入单号**；不匹配则取消。
3. 成功后刷新列表/详情；失败展示服务端 `message`。
4. **强制删除** 按钮仅 `isSysAdmin` 可见；与反核销独立。

显示条件：

| 页面 | 付款 | 收款 |
|------|------|------|
| 列表/详情 | `status === 100` 且 `finance-payment.write` | `status ∈ {2,3}` 且 `finance-receipt.write` |

## 8. 非范围与后续项

| 项 | 说明 |
|----|------|
| 按笔选择性撤销核销 | 不支持；仅整单 |
| 预收池核销（write_off_source=20） | 不关联收款单，不在收款反核销范围 |
| **反预收入账** | 收款 `AdvancePoolAmount>0` 时须先处理；**二期** |
| 列表 `hasVerification` 字段 | 可选优化，用于精确控制按钮显隐 |

## 9. 验收检查清单

### 付款

- [ ] 付款完成且已核销时，强删返回 400
- [ ] 反核销后 `Status=10`，PO 明细付款状态回滚
- [ ] 反核销后强删成功
- [ ] 普通 DELETE 在已核销时被守卫拒绝
- [ ] `log_operation` 有「付款反核销」记录

### 收款

- [ ] 已核销时强删返回 400（含销项发票/核销明细文案）
- [ ] 反核销后应收 `verified_to_be` 恢复，核销流水区清空
- [ ] 主单 `Status` 仍为 2 或 3
- [ ] `AdvancePoolAmount>0` 时反核销/强删均拒绝
- [ ] 反核销后强删成功
- [ ] `log_operation` 有「收款反核销」记录
