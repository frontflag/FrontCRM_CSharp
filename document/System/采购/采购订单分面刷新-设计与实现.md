## 1. 目标与准绳

详情页刷新拆成六项。准绳均为**已保存的采购订单头 / 明细行**，刷新不改这些源字段。

| 分面 | 入口 | 做什么 |
|------|------|--------|
| 刷新状态 | 主按钮 | 只按已有单据事实重算派生状态与进度 |
| 刷新供应商 | 下拉 | 同 ID 刷头名称 + 下游（完结门控见采购参数「分面刷新」；须确认才覆盖已完结） |
| 刷新物料型号 | 下拉 | 覆盖下游 PN 快照，并按新型号**重对齐库存分桶** |
| 刷新品牌 | 下拉 | 覆盖下游品牌快照，并按新品牌**重对齐库存分桶** |
| 刷新数量 | 下拉 | 对齐到货**计划量**（只收缩超量单批次），再重算总额 / GP / 状态 |
| 刷新单价 | 下拉 | 覆盖下游采购价快照，再重算总额 / GP / 状态 |

刷新型号 / 品牌会改库存层 `purchase_pn` / `purchase_brand`（分桶键），可能换堆或新建 `stock` 汇总行，并重算备货可用量。拣货 / 装箱已引用的 `StockItemCode` **不改**。

数量 / 单价会**顺带**刷新状态。刷新状态**绝不**回写 PN、品牌、数量、单价。保存采购明细**不会**自动改库存分桶键，须显式点本分面。

**不是本功能：** 采购订单列表 / 明细列表的列表重查、浏览器 F5。

## 3. API

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/api/v1/purchase-orders/{id}/refresh/preview` | 非状态分面预检：能否刷新、是否有已完结、列出单据 |
| POST | `/api/v1/purchase-orders/{id}/refresh` | body `{ "facet": "status\|vendor\|pn\|brand\|qty\|price", "confirmCompleted": false }` |
| POST | `/api/v1/purchase-orders/{id}/refresh-item-extends` | **兼容**：等价 `facet=price`（兼容路径对 price 传 `confirmCompleted: true`） |
| POST | `/api/v1/purchase-orders/{id}/refresh-vendor-name` | 现网供应商刷新；详情须带 `confirmCompleted` 才覆盖已完结 |
| GET / PUT | `/api/v1/purchase-params/refresh-completed-facets` | 五个分面开关 |

`facet=vendor` 在 Facade 内转到现网供应商刷新结果映射。Debug「刷新采购订单状态」改为 `facet=status`，不再顺带覆盖采购价。

有已完结且参数开时：预检通过后须 `confirmCompleted=true`，否则后端拒绝。参数关且有已完结：预检即阻断，不执行。无已完结：`confirmCompleted` 可 false。刷新状态不走预检门控。

## 4. Recalculate 副作用拆分

`PurchaseOrderItemExtendSyncService.RecalculateAsync` 增加选项：

| 选项 | 到货数量 | 到货单价 | 到货品牌 | 数量校验 |
|------|----------|----------|----------|----------|
| `Default`（保存、入库、付款等） | 单批次超量则收缩 | 对齐 | 对齐 | 开 |
| `StatusOnly`（刷新状态 / 刷新单价之后 / 刷新数量之后） | 关 | 关 | 关 | 关 |
| `QtyPlanOnly`（刷新数量的计划量一步） | 单批次超量则收缩 | 关 | 关 | 开 |

分批到货仍**不得**自动扩成整单。刷新型号 / 品牌**不**跑 Recalculate（避免改到货价/量）。

## 5. 各分面下游与调用顺序

Facade：`PurchaseOrderService.RefreshDownstreamAsync`。

```text
vendor → MapVendorRefreshResultAsync（现网换供应商刷新）
price  → PurchasePriceDownstreamSync.ApplyAsync → Recalculate(StatusOnly) → 主状态
pn/brand → IdentityDownstreamSync.ApplyAsync（含库存换桶）→ 不 Recalculate
qty    → SyncArrivalNoticePlanQtyAsync → Recalculate(StatusOnly) → 主状态
status → Recalculate(StatusOnly) → 主状态
```

### 5.1 刷新状态

重算：明细 `Status` / `FinancePaymentStatus`、扩展进度、到货通知状态、销售行利润（读当前已落库采购价）、采购申请、单头主状态 / 财务状态。

不改：供应商、PN、品牌、数量、单价、请款付款流水、进项票面。

### 5.2 刷新供应商

见 [换供应商设计](./采购订单换供应商-设计与实现.md)。完结门控走采购参数「分面刷新 → 刷新供应商」：关则已完结且供应商不一致整面阻断；开则预检列出已完结单据，详情须确认后才执行（`confirmCompleted`）。编辑页换供应商保存仍走 `ApplyAsync`，不套详情确认标志。

### 5.3 刷新物料型号 / 品牌

先按采购行当前值覆盖下游快照（刷新型号只写 PN 类字段，刷新品牌只写品牌类字段），再对已改键的在库明细做分桶对齐。

| 节点 | 型号 | 品牌 |
|------|------|------|
| 到货通知 | `Pn` | `Brand` |
| 入库明细 | `PurchasePn` | `PurchaseBrand` |
| 装箱明细 | `Pn` | `Brand` |
| 报关明细 | `purchase_pn` | `purchase_brand` |
| 库存明细 `stockitem` | `purchase_pn` | `purchase_brand` |
| 库存汇总 `stock` | 按层重对齐（见下） | 按层重对齐（见下） |

默认可覆盖已完结展示快照（参数默认允许；关则整面阻断）。覆盖前详情会列出已完结单据并要求确认。报关申报单价、HS、入库/出库实绩数量、采购价**不改**。

**分桶对齐（`StockItemPurchaseIdentityRebucketService`）：**

1. 比较口径与入库过账相同：`StockType` + `RegionType` + `WarehouseId` + `PurchasePn` + `PurchaseBrand` + `SellOrderItemId`（trim + 忽略大小写）。
2. 仍落在原桶：只把汇总行上的 PN / 品牌**文案**对齐到明细层（大小写/空格），不换 `StockAggregateId`。
3. 键已变：在同会话或库中找已有桶；找不到则按 `ModuleCodes.Stock` 新建 `stock` 行（先 `SaveChanges`，避免 `stock_extend` FK），再把明细的 `StockAggregateId` 改过去。**不改** `StockItemCode`。
4. 重算旧桶与新桶：`Qty` / `QtyStockOut` ← 各层入库/出库累计，以及 Occupy / Sales / Repertory / Available。
5. 旧桶已无未删除在库明细、且数量字段全 0：软删 `stock`（及 `stock_extend`）。仍挂有明细则保留，即使数量为 0。
6. 对涉及的 (PN, Brand) 调用 `ISellOrderItemPurchasedStockAvailableSyncService.RecalculateByPurchasePnAndBrandAsync`。

### 5.4 刷新数量

**可改：** 到货通知在「本行恰好 1 条且预计数量 > 采购行数量」时收缩 `ExpectQty`，并按**现有单价**重算通知金额；然后 `StatusOnly` 重算扩展 / GP / 状态。

**禁止改：** 入库数量、库存结存、出库数量、付款数量、质检数量、报关数量。采购数量小于已收+在途则失败。

### 5.5 刷新单价

见 [下游采购价刷新](./采购订单下游采购价刷新-设计与实现.md)。写完价快照后用 `StatusOnly` 重算，**不再**顺带写品牌。

## 6. 前端

| 项 | 位置 |
|----|------|
| 分面按钮组 | `CRM.Web/src/views/RFQ/PurchaseOrderDetail.vue` |
| API | `purchaseOrderApi.refreshDownstream(id, facet, { confirmCompleted })`、`previewRefreshDownstream` |
| 文案 | `purchaseOrderDetail.refresh*`（zh-CN / en-US） |

主按钮「刷新状态」；▾ 六项。非状态分面先 `POST …/refresh/preview`：不能进行则提示；有已完结则警告列出单据，确认后 `confirmCompleted=true` 再执行。型号 / 品牌 / 数量 / 单价确认框 `type=warning`。

刷新型号 / 品牌结果摘要：`库存明细 N 条（换堆 X，新建汇总 Y，删除空汇总 Z）`。Z = 这次去掉了几条已无明细的库存汇总行，**不是**再删库存数量。

## 8. 已完结节点（按分面）

采购参数「分面刷新」五个开关，权限仍用 `system.params.purchase.refresh-vendor.*`。存储：旧布尔 `System.Purchase.AllowRefreshCompletedBizNodes`（供应商）与 JSON `System.Purchase.RefreshCompletedFacets`（pn/brand/qty/price；vendor 与旧布尔同步）。

| 分面 | 默认 | 已完结判定（预检列出） |
|------|------|------------------------|
| 供应商 | 关 | 现网：已入库到货、已过账入库、已付款、已认证/冲红进项（且供应商 ID 不一致） |
| 物料型号 / 品牌 | 开 | 到货已入库；入库已过账；库存明细已入账；装箱已备货/已出库；报关已有明细 |
| 数量 | 开 | 到货通知已入库（本分面可能收缩其计划量） |
| 单价 | 开 | 到货已入库；入库已过账；库存明细已入账；入库行已进项匹配；出库扩展已有采购价快照 |
| 刷新状态 | — | 不走本门控 |

行为：参数关且有已完结 → 整面阻断。参数开且有已完结 → 必须确认后才刷新。无已完结 → 原确认框即可。

供应商默认关：沿用现网 `AllowRefreshCompletedBizNodes`，改已完结单据上的客商身份风险高。型号等默认开：上线前这些分面本来就会覆盖已完结，默认拦住会行为倒退。要允许供应商覆盖已完结：打开本页「刷新供应商」并保存；详情仍须确认列出的单据。

编辑页换供应商保存走 `PurchaseOrderVendorChangeService.ApplyAsync`，不套详情 `confirmCompleted`。参数关时已完结且供应商 ID 仍为旧值则阻断整单保存。
