# 采购订单取消确认 — 设计与实现

**状态：** 已上线  
**页面：** 采购订单列表 `/purchase-orders` 操作列；采购订单详情 `/purchase-orders/:id` 顶栏  
**状态机：** [采购订单主状态](../采购订单主状态.md) §2.2  
**测试对照：** [采购订单取消确认-测试对照说明](../../QA/采购/采购订单取消确认-测试对照说明.md)  
**帮助：** `help/pages/采购订单_MENU_PURCHASE_ORDERS.md`（「取消确认」）

---

## 1. 目标与口径

「取消确认」= **撤回供应商确认**，把主单从 **已确认(30)** 退回 **待确认(20)**。

| 项 | 约定 |
|------|------|
| 是 | 已确认 → 待确认。退回后只能再点「供应商确认」回到 30。 |
| 不是 | 不是整单作废（取消 `-2`）。不是审批驳回（审核失败 `-1`）。 |
| 与「取消订单」 | 详情「取消订单」仅主状态 **&lt; 10**（新建 / 待审核 / 审核失败）写 `-2`。待确认及之后界面无「取消订单」。 |
| 进行中 / 采购完成 | 界面不显示「取消确认」；状态机也不允许 `50 → 20`。 |

历史缺陷：列表「取消确认」曾把主单写成 **取消(-2)**。现网界面只发 `20`。

---

## 2. 入口与权限

| 入口 | 显示条件 |
|------|----------|
| 列表操作列（展开为红色按钮；收起为 `...` 危险项） | `purchase-order.write`，且主状态 **恰好为 30** |
| 详情顶栏「取消确认」 | 同上（`canWritePo` + `normalizePurchaseOrderMainStatus === 30`） |

无写权限不显示按钮；直接 `PATCH status=20` 由接口 `RequirePermission("purchase-order.write")` 拒绝。  
无新权限码、无新迁移。数据范围仍走采购订单访问控制。

确认框文案须写明退回「待确认」、**不是**取消订单，成功提示「已退回待确认」。

---

## 3. 状态流转

### 3.1 人工允许的目标（`ValidateStatusTransition`）

`30 已确认` 允许：`50 进行中`、`20 待确认`（取消确认）、`-2 取消`。

`20 待确认` 允许：`30 已确认`、`-2 取消`。

界面「取消确认」只发 **20**。后端仍允许 `30 → -2`（应急 / 改库），该路径 **不走** 下游 Guard。

### 3.2 明细同步

目标为 `20` 时 `ShouldSyncOrderAndItemStatus` 为真：本单全部明细 `purchaseorderitem.status` 写成 **20**（与主单一致）。

进入执行阶段（50、100）后明细按里程碑独立维护；取消确认发生在已确认节点，仍属前半段同步。

### 3.3 成功后的连带

1. 主表 `status`、`ModifyTime`、`ModifyByUserId`。  
2. 明细 `status` 同步（§3.2）。  
3. 更改日志：`fieldName=status`，`fieldLabel=订单状态`，原值「已确认」，新值「待确认」。  
4. 订单旅程 `PO_STATUS_CHANGED`，`Remark=取消供应商确认`。  
5. 关联销售明细扩展、采购申请占用、本单各行采购明细扩展重算。

退回待确认后：申请付款、通知到货、采购单打印仍要求 **已确认及之后**，因此这些入口会隐藏或提示。

## 4. 下游拦截（有则禁止退回）

仅当 **当前=30 且目标=20** 时调用 `PurchaseOrderRevertVendorConfirmGuard.EnsureCanRevertAsync`。  
任一命中则抛 `InvalidOperationException`，主单保持已确认。提示格式：

> 存在下游单据，不能取消确认并退回待确认：{类别 单号…}。请先处理这些单据。

每类最多列出 5 个单号。货代单号 **不拦截**。

| 类别 | 命中条件 | 提示前缀 |
|------|----------|----------|
| **付款单** | 付款明细挂本单 `PurchaseOrderId` 或本单明细 ID；付款单未删除，且状态 **不是** 取消(-2)、审核失败(-1)。**含在途未付请款。** 已取消 / 已删除的付款单不拦。 | `付款单` |
| **到货通知** | 未删除，且 `PurchaseOrderId` 为本单或 `PurchaseOrderItemId` 属于本单明细。任意状态的有效通知都拦。 | `到货通知` |
| **入库单** | 未删除、**已过账**、类型为 **采购入库**（`StockInTypeCode.IsPurchaseReceipt`）。来源：到货通知 `SourceId`，或 `stockinitemextend.purchase_order_item_id`。草稿 / 待入库、非采购入库类型不拦。 | `入库单` |
| **进项发票** | 未删除。按发票明细 `PurchaseOrderCode` 等于本单号，或发票明细 `StockInId` 属于上述到货通知对应入库单。本版 **不** 按发票业务状态再过滤。 | `进项发票` |

多类同时存在时，提示用中文分号拼接。

## 5. 实现路径

```text
UI（仅 status=20）
  → PATCH /api/v1/purchase-orders/{id}/status  { status: 20 }
  → PurchaseOrdersController.UpdateStatus（purchase-order.write）
  → PurchaseOrderService.UpdateStatusAsync
       ValidateStatusTransition(30 → 20)
       PurchaseOrderRevertVendorConfirmGuard.EnsureCanRevertAsync
       写主单 + 同步明细 + 更改日志 + 旅程 + 扩展重算
```

## 6. 与取消订单、API 应急的关系

| 路径 | 界面 | 后端 |
|------|------|------|
| 取消确认 | 只发 `20` | Guard + 明细同步到 20 |
| 取消订单 | 仅 `&lt; 10` 发 `-2` | 无 Guard；明细同步到 -2 |
| 应急 `30 → -2` | 界面不提供 | 状态机允许；**不跑** Guard |

历史已误写成取消的已确认单 **不会** 自动回到待确认，需另行改库。

## 7. 日志

| 存储 | 取消确认时 |
|------|------------|
| 详情「更改日志」`log_change_fldval` | 主表「订单状态」已确认 → 待确认。明细 `status` 同步 **不** 另写一行。 |
| 订单旅程 `log_orderjourney` | `EventCode=PO_STATUS_CHANGED`，`FromState=30`，`ToState=20`，`Remark=取消供应商确认` |

无独立动作码区分「取消确认」与「取消订单」：看更改日志 **原值**（已确认 = 取消确认；新建/待审/审核失败 = 取消订单）。
