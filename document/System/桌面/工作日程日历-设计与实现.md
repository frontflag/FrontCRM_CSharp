# 工作日程日历 — 设计与实现

> **状态：** MVP（一期已实现，待环境跑迁移后验收）  
> **入口：** `/dashboard` 右侧月历（与控制台共用，不另开菜单）  
> **帮助：** [控制台](../../../help/pages/控制台_MENU_DASHBOARD.md)  
> **QA：** [工作日程日历-测试对照说明](../../QA/系统/工作日程日历-测试对照说明.md)  
> **权限：** 任务 `work-task.read` / `work-task.write`；蓝/绿点分别要求 `rfq.read` / `sales-order.read`  
> **DDL：** `scripts/ensure_work_task_postgresql.sql`；迁移 `20260913180000_WorkCalendarAndTask`  

桌面首页工作日程：按月查看「当天发生了什么、当天要做什么」，并安排客户跟进任务。  
圆点语义与图1 旧图例（蓝=日程 / 红=逾期 / 绿=交付）**不同**，以本文为准；桌面与日历必须同一套规则。

## 1. 目标与非目标

### 1.1 目标（一期）

1. 月历展示当月每一天的圆点：蓝=已分配需求、绿=已审核订单、橙=有安排任务。  
2. 点某一天：列出当天需求、销售订单、任务；可跳转详情。  
3. 新建 / 完成 / 取消「客户跟进」任务。  
4. 任务完成后，按方案 A 写一条客户联系历史（不写下次跟进）。  
5. 数据范围 **只看自己**：需求/订单看自己当业务员的单；任务看自己当执行人的行。

### 1.2 非目标（一期不做）

| 项 | 说明 |
|----|------|
| 考核 / 评分 / 评语 | 独立考核表以后再做，本期不建表 |
| 协作人 | 可见与改状态规则未定 |
| 附件 | 以后复用 `upload_document`，BizType 预留 `WORK_TASK` |
| 截止日期 / 逾期红点 | 橙点只看开始日 |
| 父子任务 | `parent_task_id` 不建列 |
| 周期任务 | 重复跟进 = 再新建一条 |
| 团队日历 / 按数据范围看下属 | 经理要看团队另开筛选 |
| 行业新闻、交期风险 | 与本功能无关 |
| 独立菜单页 | 先做桌面月历 |

### 1.3 产品定稿（已冻结）

| 项 | 口径 |
|----|------|
| 蓝点 | 自己当业务员的需求，主状态 ≥ 已分配且未取消；日期 = **首次变为已分配的那天** |
| 绿点 | 自己当业务员的销售订单，状态 ≥ 审核通过（10/20/100）；日期 = **首次变为审核通过的那天** |
| 橙点 | 自己是执行人、未删除、未取消的任务（含已完成）；日期 = **开始日** |
| 范围 | 只看自己，不跟销售数据范围 |
| 客户跟进 vs 联系历史 | 方案 A：任务是计划；完成后写联系历史；不写 `NextFollowUpTime` |
| 任务本体 | 对象类型/对象 ID/标题/内容与执行字段同一行，不拆「任务说明书」表 |
| 考核 | 不进任务表；以后独立表用 `TaskId` 关联 |

## 2. 日历规则

### 2.1 日切与时区

- 公司日历日：`Asia/Shanghai`。  
- `assigned_at` / `approved_at` 存 UTC，聚合成点时转到上海日历日。  
- 任务 `start_date` 存 **date**（无时区），语义即上海日历日，不作 UTC 换算。

### 2.2 圆点展示

| 颜色 | 条件 | 一天最多 |
|------|------|----------|
| 蓝 | 当日 `rfqCount > 0` | 1 个 |
| 绿 | 当日 `soCount > 0` | 1 个 |
| 橙 | 当日 `taskCount > 0` | 1 个 |

悬停（或点日期后的摘要）显示「需求 N / 订单 N / 任务 N」。不要按单数堆多个同色点。

无权限看需求或订单时，对应计数当 0，不报错。

### 2.3 「自己」

| 数据 | 归属字段 |
|------|----------|
| 需求 | `rfq.sales_user_id` = 当前用户 Id |
| 销售订单 | `sellorder.sales_user_id` = 当前用户 Id |
| 任务 | `work_task.assignee_user_id` = 当前用户 Id |

创建人把任务派给同事后，**橙点出现在执行人日历上**，创建人自己的月历不再因该任务打橙点。

### 2.4 蓝点：需求已分配日

需求没有审核流。主状态见 `RfqMainStatus`：0 待分配 → 1 已分配 → 2 报价中…；8 已取消。

| 计入蓝点 | 不计入 |
|----------|--------|
| 状态 ∈ {1,2,3,4,5,7}（已分配及之后，含已关闭）且 `assigned_at` 落在该日 | 待分配(0)、已取消(8)、软删、`assigned_at` 空 |

`assigned_at` 只在 **0→1**（或新建时直接落到已分配）时写一次，之后状态再变不改。

写入时机（实现须改 `RFQService`）：

1. 新建需求时明细已分到采购员，主单直接 `Status=1`：`assigned_at = CreateTime`（UTC）。  
2. `TryAdvanceRfqToAssignedWhenAllItemsHavePurchaserAsync` 首次 0→1：`assigned_at = UtcNow`。

### 2.5 绿点：订单审核通过日

销售订单主状态见 `SellOrderMainStatus`：1 新建 → 2 待审核 → **10 审核通过** → 20 进行中 → 100 完成。

| 计入绿点 | 不计入 |
|----------|--------|
| 状态 ∈ {10,20,100} 且 `approved_at` 落在该日 | 新建、待审核、审核失败(-1)、取消(-2)、软删、`approved_at` 空 |

`approved_at` 只在 **首次进入 10** 时写一次（`SalesOrderService.UpdateStatusAsync`）。之后进行中/完成不改；若通过后又取消，状态不再 ≥10，绿点不再出现（历史 `approved_at` 保留）。

### 2.6 历史回填

现网没有这两列。迁移时：

1. 有列后，对存量：从 `log_change_fldval` 取该单 **第一次** 状态变为「已分配」/「审核通过」的 `ChangedAt`。  
2. 无日志：需求当前状态 ≥ 已分配且未取消 → `assigned_at = create_time`（近似）；订单当前状态 ≥10 → `approved_at` 留空（避免把修改日当成通过日）。  
3. 回填后仍为空的单：不打点。

## 3. 任务模型

### 3.1 原则

- 一行即一条可执行任务：挂载对象 + 标题内容 + 开始日 + 执行人 + 状态。  
- 不拆任务本体表。  
- 考核不进本表。一期不建考核表。  
- 附件、协作人一期不做。

### 3.2 表 `work_task`

| 列 | 类型 | 说明 |
|----|------|------|
| `id` | varchar(36) PK | GUID |
| `create_time` | timestamptz | UTC |
| `create_by_user_id` | varchar(36) | 创建人 |
| `modify_time` | timestamptz | 可空 |
| `status` | smallint | 见 §3.4 |
| `object_type` | varchar(32) | 一期仅 `CUSTOMER` |
| `object_id` | varchar(36) | 客户 Id，必填 |
| `title` | varchar(200) | 必填，去空白 |
| `content` | varchar(2000) | 可空 |
| `start_date` | date | 开始日（上海日历日），橙点用此列 |
| `priority` | smallint | 0=P0 最紧急 … 3=P3 一般 |
| `assignee_user_id` | varchar(36) | 执行人，默认创建人 |
| `completed_at` | timestamptz | 完成时 UTC |
| `completed_by_user_id` | varchar(36) | 完成人 |
| `contact_history_id` | varchar(36) | 完成后写入的联系历史 Id，防重复写 |
| `is_deleted` | bool | 软删 |

索引：

- `(assignee_user_id, start_date)` WHERE `is_deleted = false`  
- `(object_type, object_id)` WHERE `is_deleted = false`

预留对象类型（一期不实现 UI）：`CUSTOMER_CONTACT`、`VENDOR`、`RFQ`、`QUOTE`、`SELL_ORDER`、`PURCHASE_ORDER`、`STOCK_ITEM`、`RECEIVABLE`。  
一期接口拒绝非 `CUSTOMER`。

### 3.3 一期不建的字段

`parent_task_id`、`due_date`、协作人表、考核人/分/评语、附件外键。  
以后考核：`work_task_assessment`，`task_id` 唯一，不回写进任务表（列表可用 JOIN 或只读冗余）。

### 3.4 状态

| 值 | 含义 |
|----|------|
| 10 | 待开始 |
| 20 | 进行中 |
| 30 | 完成 |
| 90 | 取消 |

```
待开始 → 进行中 → 完成
待开始 / 进行中 → 取消
```

- 新建默认待开始。  
- 完成、取消为终态：不可改 `object_type` / `object_id` / `start_date`；标题、内容仍可改。  
- 无「暂停」。  
- 软删：列表与橙点不可见；不物理删。

谁能改：创建人、执行人；具备 `work-task.write`。不能改别人既非创建也非执行的任务。

### 3.5 客户跟进表单（一期唯一类型）

| 字段 | 规则 |
|------|------|
| 客户 | 必选；须 `customer.read` 且当前用户对该客户可见 |
| 标题 | 必填，最长 200 |
| 内容 | 可空，最长 2000 |
| 开始日期 | 必填；允许过去日（补录） |
| 紧急程度 | P0–P3，默认 P2 |
| 执行人 | 默认自己；可改为其他启用员工 |

选客户后 `object_type=CUSTOMER`，`object_id=客户Id`。

## 4. 方案 A：完成后写联系历史

任务完成时（`status` 10/20 → 30），若 `object_type=CUSTOMER` 且 `contact_history_id` 为空，插入一条 `customercontacthistory`：

| 联系历史字段 | 取值 |
|--------------|------|
| `CustomerId` | 任务 `object_id` |
| `Type` | `other`（不新增客户页筛选项） |
| `Subject` | 任务标题 |
| `Content` | 任务内容 |
| `Time` | 完成时刻（UTC） |
| `NextFollowUpTime` | **null**（下次跟进再新建任务） |
| `Result` | `任务完成` |
| `OperatorId` | 完成人 |

写成功后回写 `contact_history_id`。再次点完成：已是 30 则幂等成功，不再插第二条。

客户详情「联系历史」仍可手工增删；**不要**把「下次跟进」再当成第二套计划源。客户页不出现的下次跟进，一律走日历任务。

## 5. API（拟定）

基路径 `/api/v1`。一律登录。模拟登录可读日历与任务，写操作按现网模拟策略（与通知已读类似：能看、写要明确是否落库；一期写接口在模拟下拒绝或按真实操作人，实现时与审批桌面对齐并写进 QA）。

### 5.1 月聚合

`GET /work-calendar/month?year=2026&month=9`

返回该月每天：

```json
{ "year": 2026, "month": 9, "days": [ { "date": "2026-09-12", "rfqCount": 2, "soCount": 1, "taskCount": 3 } ] }
```

只含 count>0 的日亦可；前端无记录当天当 0。  
禁止把当月需求/订单/任务全量详情一次拉回。

### 5.2 日明细

`GET /work-calendar/day?date=2026-09-12`

三块数组：需求（id、单号、客户名）、订单（id、单号、客户名）、任务（id、标题、状态、紧急程度、客户名）。  
无对应读权限的块返回空数组。

### 5.3 任务

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/work-tasks` | 新建，默认待开始 |
| GET | `/work-tasks/{id}` | 创建人或执行人 |
| PATCH | `/work-tasks/{id}` | 改标题/内容/开始日/优先级/执行人/进行中 |
| POST | `/work-tasks/{id}/start` | 待开始 → 进行中（可并入 PATCH） |
| POST | `/work-tasks/{id}/complete` | → 完成 + 方案 A |
| POST | `/work-tasks/{id}/cancel` | → 取消 |
| POST | `/work-tasks/{id}/delete` | 软删（或 DELETE） |

列表不必单独做一期；日明细 + 月历足够。

## 6. 界面（一期）

位置：`DashboardView` 右侧（或欢迎区下右栏）月历，交互对齐产品稿：当月网格、今日高亮、上月/下月、图例「蓝需求 / 绿订单 / 橙任务」。

点日期：抽屉或浮层展示当天三块列表 +「新建跟进」。  
新建：选客户、标题、内容、开始日（默认所点日期）、紧急程度、执行人。

采购主部门用户同样看到月历：无 `rfq.read` / `sales-order.read` 时蓝绿为空，橙点仍是自己的任务。

## 7. 权限与菜单

| 码 | 用途 |
|----|------|
| `work-task.read` | 看自己的任务与橙点 |
| `work-task.write` | 新建/改/完成/取消/软删（须为创建人或执行人） |
| `rfq.read` | 蓝点与当天需求列表 |
| `sales-order.read` | 绿点与当天订单列表 |
| `customer.read` | 新建跟进时选客户；完成时写联系历史 |

无 `work-task.read`：月历仍显示，橙点全 0，不能建任务。  
权限脚本与角色种子在实现时列入 `scripts/`，本文更新 DDL 行。

桌面 `/dashboard` 不另挂菜单项。埋点页保持 `TelemetryCatalog`「工作台」。

## 8. 实现要点

1. **补列（禁止挂进 RFQ/SO 实体映射）**  
   - `rfq.assigned_at timestamptz NULL`  
   - `sellorder.approved_at timestamptz NULL`  
   这两列 **不** 映射到 `RFQ` / `SellOrder`，避免生产漏跑脚本时整表 SELECT 因 `42703` 拖垮审批、订单、桌面。  
   写入走 `IWorkCalendarStampWriter` 独立 `UPDATE`；月历走原始 SQL，缺列/缺表时该块为空、不抛 500。  
   API 启动执行幂等 `ADD COLUMN IF NOT EXISTS` / `CREATE TABLE IF NOT EXISTS work_task`（**不**做历史回填、不写权限）。  
   历史回填仍用 `scripts/ensure_work_task_postgresql.sql`。写入与回填见 §2.4–§2.6。  

2. **聚合查询**  
   三条按日 `GROUP BY`（需求 / 订单 / 任务），再在内存按日期合并。过滤：未软删、归属当前用户、状态集合、日期落在 `[monthStart, nextMonth)`（上海）。  

3. **字段变更日志**  
   任务标题、内容、开始日、状态、执行人、紧急程度写入 `log_change_fldval`（新 `BizType`，如 `WorkTask`），规则见 [业务字段变更日志](../业务字段变更日志-设计与实现.md)。  
   需求/订单补列写入本身不必另打点；状态推进仍走现有 RFQ/SO 状态日志。  

4. **客户可见性**  
   完成写联系历史与选客户，复用现有客户数据权限，不可越权写他人不可见客户。  

5. **前端**  
   不引入完整日程中间件；月历可用轻量自绘或 Element Plus DatePicker 面板改圆点。
