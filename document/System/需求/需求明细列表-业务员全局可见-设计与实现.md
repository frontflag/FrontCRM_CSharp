## 1. 产品结论（三层）

本页权限本来就该是三层；**现网 `/rfq-items` 后两层未按行落地**（看见行 ≈ 客户名下发 ≈ 详情/生成 SO 按钮都在）。本次不是「只改 WHERE」，而是：

| 层 | 含义 | 本次 |
|----|------|------|
| **数据行** | 列表能不能扫到这条明细 | **放宽**：一线业务员、销售部门经理在本页可见全公司未删明细 |
| **敏感字段** | 客户身份能否明文 | **不放宽**：仍仅「匹配集合」明文 |
| **业务操作** | 详情、生成销售订单 | **不放宽**：仍仅「匹配集合」可做；前后端一起拦生成 SO |

匹配集合按角色：

| 角色 | 匹配集合（客户明文 + 详情 + 生成 SO） |
|------|----------------------------------------|
| 一线业务员 | **仅自己**（`RFQ.SalesUserId == 当前用户`） |
| 销售部门经理 | **自己 + 本部门 + 子部门员工**（组织职级：经理只看员工，不含同级经理） |
| 销售部门总监、`SYS_BIZ_MANAGER`、`SYS_MANAGER`、`SYS_ADMIN` | **豁免**：三层均维持现网，不套本补丁 |

空 `SalesUserId` 视为不在匹配集合内。

**不改：** `/rfqlist` 行过滤、报价列表 `/quotes`、报价桌面 `/quote-desktop`、采购保护时长、`CanQuote`、报表 `/reports/sales` 需求 Tab。

## 2. 角色判定（前后端同一套）

输入：`UserPermissionSummaryDto` / 前端 `authStore.user`（`identityType`、`roleCodes`、`isSysAdmin`、`isSysManager`、`isBizManager`、`hasBizDataBypass`、`saleDataScope`）。

```text
IsExemptRfqItemListPatch
  = isSysAdmin OR isSysManager OR isBizManager OR HasBizDataBypass
    OR (IdentityType == 1 AND 角色含 DEPT_DIRECTOR)

IsSalesDeptManager
  = IdentityType == 1
    AND 角色含 DEPT_MANAGER
    AND NOT IsExemptRfqItemListPatch

IsFrontlineSalesperson
  = IdentityType == 1
    AND SaleDataScope != 4
    AND NOT IsExemptRfqItemListPatch
    AND NOT IsSalesDeptManager

WidenRfqItemListRows = IsFrontlineSalesperson OR IsSalesDeptManager
```

组织角色大小写不敏感，与 `SalesDirectorSelfApprovalRules` / `ResolveOrgRoleLevel` 一致。

采购员、采购经理/总监、财务/物流身份：**不**因本补丁放宽销售侧列表。他们仍走原销售∨采购过滤（含需求保护）。

## 3. 匹配集合（敏感字段 + 操作）

复用 `IDataPermissionService.GetAllowedUserIdsForDataScopeAsync`。

| 调用方 | `includeChildren` | 结果 |
|--------|-------------------|------|
| 一线业务员 | （不调，集合 = `{ 当前用户 Id }`） | 仅自己 |
| 销售部门经理 | **`true`** | 本人 + 本部门路径下子部门中、职级 ≤ 员工（`DEPT_EMPLOYEE`）的用户 |

经理集合**不含**同级其他经理。这些行会出现在全局列表中，但客户隐藏、详情/生成 SO 禁止。

## 4. 列表行可见（仅本页查询）

改 `CRM.Infrastructure/RFQ/RfqItemListFilter.cs` 的数据范围段（看板共用同一方法）。

现网：`SaleDataScope!=0 && PurchaseDataScope!=0` 时按销售 `SalesUserId` ∨ 采购分配/保护池过滤。

补丁：当 `WidenRfqItemListRows` 为真时，**销售侧条件视为恒真**（等价本页销售范围=全部），采购侧条件原样保留。

- `SaleDataScope==4` 的一线不会被标成 `IsFrontlineSalesperson`，不放宽。
- 豁免角色不进该分支，过滤与现网完全相同。
- **禁止**改 `FilterRFQsAsync`（`/rfqlist`）。

客户关键字：对 `WidenRfqItemListRows` 用户，关键字命中须同时满足 `SalesUserId ∈ 匹配集合`（避免用客户名搜出外部门单）。无客户查看权（521）时现网已丢掉关键字，保持。

物料关键字里的客户料号：无行级明文时不要用 `CustomerMpn` 命中外部门行；`CanViewCustomerInList` 仍是整页开关，行级抹掉后应用「仅匹配集合行才允许 CustomerMpn 参与搜索」。实现可在 Filter 里对 widen 用户加：

`(CustomerMpn 匹配 AND SalesUserId ∈ 匹配集合) OR Mpn 匹配`。

## 5. 行级脱敏与能力位

### 5.1 列表 DTO

`RFQItemListItem` 增加：

| 字段 | 含义 |
|------|------|
| `CanViewCustomerOnRow` | 客户明文（匹配集合内，且现网 `CanViewCustomerInList` / 非 521） |
| `CanOpenRfqDetail` | 可进需求详情 |
| `CanGenerateSalesOrder` | 可从本行报价生成销售订单 |

一线 / 经理：后两个 = `SalesUserId ∈ 匹配集合`。  
豁免 / 非 widen：三个均为 true（再叠 521：客户仍整页不可见）。

当 `CanViewCustomerOnRow == false` 时服务端清空：

- `CustomerId`、`CustomerName`
- `CustomerMpn`、`CustomerBrand`（客户侧属性，避免料号还原客户）

**保留** `SalesUserId` / `SalesUserName`（列表本就要看谁的单）。

组装点：`RfqItemListQuery.GetPagedAsync` 映射循环内，用已解析的 summary + 匹配集合，不要在 SQL 里拼客户名后再靠前端藏。

复制到篮子、导出若走同一 DTO，自动带脱敏。复制行文案不得拼接已抹掉的客户名。

### 5.2 需求详情 `CanAccessRFQ`

一线：**不改**。非本人直链 `/rfqs/:id` 仍 403。

销售经理：现网 `PassesSaleAccessToRfqAsync` 在 `SaleDataScope==2` 时 `includeChildren: false`，子部门详情会 403，与「下属含子集部门且允许详情」冲突。

**最小放宽（仅经理销售侧访问，不改列表）：**

- `PassesSaleAccessToRfqAsync`：若 `IsSalesDeptManager`，允许用户集合用 `GetAllowedUserIdsAsync(includeChildren: true)`，**忽略**该次的 scope 2/3 `includeChildren` 差。
- `FilterRFQsAsync` / `/rfqlist` **不**改。经理在需求主列表仍按部门 `SaleDataScope`；从本页点详情可打开子部门需求。

一线不要走这条。总监豁免，保持现网（通常 scope 3 已含下级）。

### 5.3 客户页签

- 选中行 `CanViewCustomerOnRow == false`：**不渲染**右栏「客户」页签（`AppLayout` `RFQItemList` 的 `r-customer` 按行动态）。
- 从明文行切到脱敏行时若停在客户，切回 **物料**。
- 不请求 `GET /api/v1/customer-workspace?source=rfqItem`。
- 网关仍要求 `CanAccessRFQ`；一线看外部门行时即使误请求也会 403。

521 整页无客户页签完整内容：现网逻辑保留，与行级规则叠加（521 优先：整页当不可见客户）。

## 6. 操作拦截

### 6.1 需求详情

`RFQItemList.vue`：

- `CanOpenRfqDetail == false`：隐藏详情按钮；双击进详情、Ctrl+双击进需求编辑都不走。可提示「无权查看该需求详情」。
- `goDetail` / `goEditRfqFromItem` 入口同样判断。

后端：一线靠未改的 `CanAccessRFQ`；经理靠 §5.2。

### 6.2 生成销售订单（前后端一起拦）

现网底部报价行「生成销售订单」无业务员校验；`Quote.GetById` 也不按 RFQ 销售范围拒绝；`SalesOrderCreate` 拉需求失败会 `catch` 忽略。必须三道闸。

**前端 `/rfq-items`**

- `CanGenerateSalesOrder == false`：隐藏该行及下拉中的生成 SO。
- `handleDockRowGenerateSalesOrder` 再判断一次，失败 `ElMessage` 并 return。
- 不改 `/quotes` 列表上的生成 SO 入口（报价列表权限不变）。直链仍靠后端。

**前端 `SalesOrderCreate`（quoteIds 预填）**

- 解析报价 → 需求 `SalesUserId`。
- 若当前用户 `WidenRfqItemListRows` 且需求业务员不在匹配集合：提示无权，**不要**预填明细，跳回 `returnTo` 或销售订单列表。
- 匹配集合前端可用列表行上的 `canGenerateSalesOrder`；直链没有列表行时，以需求 GET 403 或下方新接口为准，不要用「拉到报价就当有权」。

**后端（必做，防直链 / 改 query）**

在 `SalesOrderService.CreateAsync` **写库之前**：

1. 收集 `request.Items[].QuoteId`（客单必有报价）。
2. 加载报价 → `RFQItem` → `RFQ`。
3. 对每个关联 RFQ：`EnsureCanGenerateSalesOrderFromRfq(actingUserId, rfq)`  
   - 豁免 / `HasBizDataBypass`：通过。  
   - 否则：`CanAccessRFQ` 为真 **且**（非 widen 用户 或 `SalesUserId ∈ 匹配集合`）。  
   - 一线 widen：`CanAccessRFQ` 已是仅自己，双重仍正确。  
   - 经理：`CanAccessRFQ` 按 §5.2 含子集部门。
4. 失败：`UnauthorizedAccessException`（或业务异常）→ API 403，「无权从该报价生成销售订单」。

无 `QuoteId` 的备货/样品行：不走本条 RFQ 闸（现网客单约束仍要求客单有报价）。

报价桌面 / 报价列表生成 SO：若报价本就在其数据范围内，`CanAccessRFQ` 为真，行为与现网一致。

建议单测：一线用他人 `quoteId` 创建客单 → 拒绝；经理用下属（含子部门员工）报价 → 允许；同级经理的报价 → 拒绝。

## 7. 看板

`GET /api/v1/rfqs/items/analytics/*` 与列表共用 Filter → 数字自动变全局。

对 `WidenRfqItemListRows`：

| 块 | 处理 |
|----|------|
| KPI 发布客户 / 复询 | **保留个数**（无数、无名单） |
| 排行「客户 Top10」 | **面板保留**，条数仍按全局明细聚合；**名称按行脱敏**（见下） |
| 业务员 / 物料 / 品牌 Top10 | 名称与现网相同（无客户身份） |

**客户 Top10 名称（不要整页 `maskCustomerNames`）：**

现网 `maskCustomerNames` 会把 10 行名字全部打成 `—`，经理的下属客户也会没了。改为按行：

- 该客户分组内 **至少一条** 明细的 `RFQ.SalesUserId ∈ 匹配集合` → 名称明文（一线=自己的客户；经理=自己或下属的客户）。
- 否则 `Name = "—"`，**同时清空 `Id`**（避免用主键跳客户）。
- `OrderCount` 仍是该客户在本页全局筛选下的明细条数（可大于「自己的单」）。
- 521 / 无 `customer.info.read`：仍整表打 `—`（现网 `maskCustomerNames`）。

豁免角色、报表 `/reports/sales` 需求 Tab：**不**改。

## 14. 请确认的实现细节（已按讨论写入本文）

1. 下属 = 本部门 + **子部门员工**，经理操作含详情与生成 SO。  
2. 生成 SO **前后端一起拦**。  
3. 客户 Top10 **保留面板**，名称按匹配集合按行脱敏（自己/下属明文，其余 `—`），KPI 个数保留。  
4. 经理 `CanAccessRFQ` 为子部门详情做最小放宽；**需求主列表过滤不放宽**。

若第 4 点改为「连 CanAccessRFQ 都不动」，则部门 `SaleDataScope=2` 时经理对子部门行：列表能见、客户可按匹配集合明文，但点详情/生成 SO 仍 403。与「下属行允许详情/生成 SO」不一致，故草案采用第 4 点。
