**文档版本**: 1.0  
**创建日期**: 2026-06-29  
**适用范围**: 需求主表（`RFQ`，`/rfqs` 列表、`/rfqs/:id` 详情）  
**关联文档**: [标签系统 PRD](../../标签系统PRD.md)、[业务详情页面规范](../../规范/UI规范/业务详情页面规范.md)、[RFQ 主状态枚举](../../../System/RFQ主状态枚举.md)

## 1. 背景与目标

### 1.1 问题描述

销售在跟进需求过程中，需要一种**轻量、主观、可随时增删**的标记方式，表达「加急」「重点跟进」「需二次寻源」「追单」等跟进意图。现有 RFQ 主表字段（目标类型、重要程度、主单/明细状态）描述的是**结构化业务数据**，与跟进标记的使用人员、变更频率、应用场景不同，不能替代标签。

### 1.2 功能目标

- 对**需求主表**（实体编码 `RFQ`）打标签：系统预设标签 + 用户自定义标签
- 在需求主列表、需求详情展示标签，并支持按标签 **AND** 筛选
- 严格的**查看 / 编辑**权限：采购不可见；仅创建人与当前业务员可改
- 打/删标签写入统一操作日志（`log_operation`），**不**联动业务状态与通知

### 1.3 用户场景

| 场景 | 说明 |
|------|------|
| 加急跟进 | 业务员对某需求打「加急」，便于自己在列表中筛选；与表单「目标类型=紧急需求」并存，含义不同 |
| 催采购再询价 | 对当前报价不满意，打「需二次寻源」，提醒自己继续催采购，不绑定明细「查无报价」等状态 |
| 追客户下单 | 报价后客户犹豫，打「追单」，在列表中集中筛选待催单需求 |
| 个人备忘 | 业务员创建 RFQ 域自定义标签（如「等客户确认规格」），仅本人可选用 |

## 3. 标签定义

### 3.1 实体编码

| 字段 | 值 |
|------|-----|
| `entityType` | `RFQ` |
| `entityId` | 需求主表 `rfq.id`（GUID） |

与收藏功能 `RFQ_FAVORITE_ENTITY_TYPE = 'RFQ'` 保持一致。

### 3.2 系统预设标签（首期）

| 名称 | 编码建议 | 颜色 | 业务含义（产品文案） |
|------|----------|------|----------------------|
| 加急 | `RFQ_URGENT` | `#E53935` | 销售主观认为需优先处理；与「目标类型=紧急需求」并存，前者为跟进标记，后者为建单分类 |
| 重点跟进 | `RFQ_KEY_FOLLOW` | `#FB8C00` | 销售主观认为需持续关注；与「重要程度 1–10」并存，前者为动态标记，后者为建单字段 |
| 需二次寻源 | `RFQ_RE_SOURCE` | `#1E88E5` | 当前报价不满意，需继续催采购询价；不精确对应明细「查无报价」等状态，为统称 |
| 追单 | `RFQ_FOLLOW_ORDER` | `#8E24AA` | 跟进客户、催客户下订单；不精确对应报价/订单状态，为统称 |

**规则：**

- `Type = 1`（系统标签），`Scope` 含 `RFQ`，`Status = 1`（启用）
- **可多选**：同一 RFQ 可同时拥有多个系统标签
- 管理员**停用**某系统标签后：已打上的标签**仍展示**；业务员/创建人**可移除**
- 用户**不可**创建与上述 4 个名称**完全相同**（ trim 后精确匹配）的个人标签

### 3.3 用户自定义标签

| 规则 | 说明 |
|------|------|
| Scope | 限定为 `RFQ` |
| 创建 | 在 `ApplyTagsDialog` 内 Enter 新建 |
| 选用范围 | **仅标签定义创建者**可在**自己的 RFQ** 上使用该自定义标签 |
| 可见性 | 见 §4.2；无 RFQ 标签查看权的用户不可见 |
| 同名 | 禁止与系统 4 标签同名；用户标签之间允许重名（不同 Owner） |

### 3.4 与现有 RFQ 字段的关系

**并存，不联动，不互斥：**

| 现有字段 | 与标签关系 |
|----------|------------|
| `targetType`（含「紧急需求」） | 建单时分类；标签「加急」为跟进中主观标记 |
| `importance` / `importanceLevel` | 建单时重要程度；标签「重点跟进」为动态标记 |
| `rfq.status` / 明细 `status` | 流程状态；标签不改变任何状态 |
| 明细「查无报价」 | 采购操作结果；标签「需二次寻源」为销售主观统称 |

详情页标签区域须展示简短说明（中/英 i18n），提示标签与上述字段**用途不同**。

## 4. 权限模型

### 4.1 角色定义

| 角色 | 判定 |
|------|------|
| **创建人** | `rfq.createByUserId == currentUserId` |
| **当前业务员** | `rfq.salesUserId == currentUserId`（非空） |
| **原业务员** | 曾为 `salesUserId`，主表更换业务员后**不再**属于当前业务员 |
| **业务员上级** | 对 `rfq.salesUserId` 满足销售数据范围 **`SaleDataScope = 2`（本部门）或 `3`（本部门及下级）** 的用户，且该用户**不是**当前业务员本人；与 RFQ 列表销售侧可见范围一致 |
| **系统管理员** | `IsSysAdmin == true` |
| **采购方向** | 仅通过采购数据权限访问 RFQ 的用户（`PassesPurchaseAccessToRfqAsync` 且不满足销售侧查看标签条件） |

**业务员为空时：** 仅**创建人**可打/删标签；更换业务员后标签**保留**，**新业务员**获得打/删权限，**原业务员**失去打/删及查看权限；**创建人永久保留**打/删权限（不因换业务员而失效）。

### 4.2 权限矩阵

| 角色 | 查看标签 | 打标签 / 移除标签 |
|------|:--------:|:-----------------:|
| 创建人 | ✓ | ✓ |
| 当前业务员（`salesUserId` 非空） | ✓ | ✓ |
| 业务员上级 | ✓ | ✗ |
| 系统管理员 | ✓ | ✗ |
| 采购方向人员 | ✗ | ✗ |
| 其他销售（无上述身份） | ✗ | ✗ |
| 换岗后的原业务员 | ✗ | ✗ |

**查看范围说明：** 具备查看权限的用户，可看到该 RFQ 上**全部**已打标签（含系统标签与他人创建的自定义标签名称）。  
**编辑范围说明：** 创建人与当前业务员可移除该 RFQ 上**任意**已打标签（含对方打的标签）。

### 4.3 主单状态

RFQ **已关闭（7）/ 已取消（8）** 后，创建人与当前业务员**仍可**打/删标签。

### 4.4 接口级脱敏（强制）

| 接口 | 无查看权限时的行为 |
|------|-------------------|
| `GET /api/v1/rfqs` 列表项 | 不返回 `tags` 字段（或 `tags: null`，前端不渲染标签列内容） |
| `GET /api/v1/rfqs/{id}` 详情 | 不返回 `tags` 字段 |
| `GET /api/v1/tags/entities/RFQ/{id}` | **403** 或空列表（推荐 403 + 明确文案） |
| `POST /api/v1/tags/apply`、`/remove`（`entityType=RFQ`） | **403**，非创建人/当前业务员 |

**禁止**仅在前端隐藏：采购等角色通过 API 不得读到标签数据。

### 4.5 标签筛选权限

- 搜索栏「标签筛选」仅对**具备 RFQ 标签查看权**的用户展示（销售侧：创建人/业务员/上级/管理员）
- 采购方向用户**不展示**标签筛选项
- 筛选项数据源：系统 RFQ 标签 + **当前用户自己创建的** RFQ 自定义标签

## 5. 功能详细设计

### 5.1 详情页（`RFQDetail`）

参考 `SalesOrderDetail` 与 [业务详情页面规范](../../规范/UI规范/业务详情页面规范.md)：

| 位置 | 要求 |
|------|------|
| 基础信息区 | 新增「标签」行（`info-item--span-all`）：`TagListDisplay` + 说明文案 |
| 操作按钮 | 有编辑权限时显示「添加标签」，打开 `ApplyTagsDialog` |
| CaptionBar | 可选：在标题行 status pill 旁展示**系统标签**摘要（空间不足时仅基础信息区展示即可，首期至少基础信息区） |
| 无权限 | 不渲染标签行；不显示「添加标签」 |

`ApplyTagsDialog` 参数：

- `entity-type="RFQ"`
- `entity-ids="[rfqId]"`
- 可选标签列表：`GET /tags?entityType=RFQ` + 当前用户自定义 RFQ 标签

### 5.2 主列表（`RFQList`）

| 项 | 要求 |
|----|------|
| 标签列 | 新增列，展示 `TagListDisplay`（多标签换行/省略策略与订单列表一致） |
| 无权限用户 | 不展示该列（或列内恒为 `—`；推荐**隐藏整列**） |
| 筛选 | 搜索栏增加标签多选；选中后与 keyword、status、客户、日期等 **AND** |
| 筛选逻辑 | 默认 **OR**：含任一选中标签的 RFQ；若后续需「同时含全部标签」可扩展，首期 **OR** 即可 |

### 5.3 打标签交互

复用 `ApplyTagsDialog`：

1. 展示已选标签，点击移除（仅 UI 预选，确认后提交）
2. 搜索 / 点选系统标签与个人 RFQ 标签
3. Enter 创建个人标签（Scope=`RFQ`，校验不与系统标签同名）
4. 确认：调用 `POST /tags/apply` 与 `POST /tags/remove` 的 diff

### 5.4 移除标签

- 与打标签**相同权限**（创建人 + 当前业务员）
- 在详情 `TagListDisplay` 或弹窗内移除均可（首期与 SO 一致：弹窗内 diff + 可选 chip 移除）

## 6. 数据与接口

### 6.1 存储

沿用现有表，无新表：

| 表 | 用途 |
|----|------|
| `tag_definition` | 系统 / 用户标签定义 |
| `tag_relation` | `EntityType='RFQ'`, `EntityId=rfq.id` |
| `log_operation` | 打/删标签审计 |

### 6.2 种子数据

脚本建议路径：`scripts/rfq_system_tags_postgresql.sql`

插入 4 条系统标签（若 `Code` 已存在则 skip），`Scope='RFQ'`，颜色见 §3.2。

### 6.3 API 变更

#### 6.3.1 标签应用（增强）

`POST /api/v1/tags/apply`、`POST /api/v1/tags/remove`

当 `entityType == 'RFQ'` 时，服务端须：

1. 加载 RFQ 主表
2. 校验当前用户是否为**创建人**或**当前业务员**（§4.1）
3. 通过后调用现有 `TagApplyService`
4. 写 `log_operation`（§7）
5. 自定义标签创建时：`Scope` 含 `RFQ`；校验名称不与系统 4 标签同名

#### 6.3.2 获取实体标签（增强）

`GET /api/v1/tags/entities/RFQ/{rfqId}`

- 校验查看权限（§4.2）
- 返回该 RFQ 全部 `tag_relation` 关联的标签定义（**含已停用**系统标签，仍展示）

#### 6.3.3 需求列表（增强）

`GET /api/v1/rfqs`

**Query 新增：**

| 参数 | 类型 | 说明 |
|------|------|------|
| `tagIds` | string[] 或逗号分隔 | 含任一标签的 RFQ（OR）；与其他条件 AND |

**Response 列表项新增（仅有查看权时）：**

```json
{
  "tags": [
    { "id": "...", "name": "加急", "color": "#E53935", "type": 1 }
  ]
}
```

无查看权：省略 `tags` 或 `null`。

实现建议：先按现有条件分页，再对当前页 batch 查 `tag_relation`；或 tagIds 预筛 entityId 再 intersect 分页结果（数据量大时需索引 `tag_relation(EntityType, EntityId)`）。

#### 6.3.4 需求详情（增强）

`GET /api/v1/rfqs/{id}`

- 有查看权：返回 `tags` 数组（结构同列表）
- 无查看权：不返回 `tags`

## 7. 操作日志

使用 `ILogOperationAppendService.AppendAsync`：

| 字段 | 值 |
|------|-----|
| `bizType` | `RFQ` |
| `recordId` | `rfq.id` |
| `recordCode` | `rfq.rfqCode` |
| `actionType` | `需求打标签` / `需求移除标签`（或合并为 `需求标签变更`） |
| `operationDesc` | 例：`添加标签：加急、追单` / `移除标签：加急` |
| `operatorUserId` | 当前用户 |

首期不在 RFQ 详情增加「操作日志」Tab；管理员在 **系统 → 操作日志** 查询。

## 8. 权限码

| 操作 | 权限 |
|------|------|
| 查看 RFQ（含标签数据） | 现有 `rfq.read` + §4 数据权限 |
| 打/删标签 | 现有 `rfq.read` + §4 身份校验（**不**单独新增 permission；**不**要求 `rfq.write`） |

说明：标签是销售跟进标记，不应与「编辑需求主表字段」强绑定。

## 10. 验收标准

### 10.1 功能

- [ ] 4 个系统标签种子数据就绪，Scope=`RFQ`
- [ ] 创建人、当前业务员可在详情打/删标签；上级、管理员仅看
- [ ] 采购账号打开 RFQ 列表/详情，API 无 `tags`，UI 无标签列/行
- [ ] 换业务员后标签保留；新业务员可改，原业务员不可见
- [ ] 创建人在换业务员后仍可打/删标签
- [ ] 主列表标签列、标签筛选（AND）生效
- [ ] 关闭/取消状态仍可打标签
- [ ] 自定义标签 Scope=RFQ，仅创建者可选；不可与系统 4 标签同名
- [ ] 打/删标签写入 `log_operation`

### 10.2 非功能

- [ ] 标签 API 对 RFQ 做服务端权限校验，不依赖前端隐藏
- [ ] 与收藏、状态筛选 AND 组合结果正确
