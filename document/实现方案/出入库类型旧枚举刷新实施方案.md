# 出入库类型旧枚举刷新 — 实施方案

> **状态：** 阶段 A 已落地（2026-08-19）  
> **设计：** [出入库类型旧枚举刷新-设计与实现](../System/物流/出入库类型旧枚举刷新-设计与实现.md)  
> **不修改** `document/EBS/`

存量：`1→10`、`2→30`、`4→40`。`stock_in` / `stock_out` 及同源类型列盘点 **`1/2/4` 已为 0**。下文 SQL 仅作幂等补刷（再跑更新 0 行）。

---

## 1. 目标与非目标

**目标**

1. 六张类型表中旧值 `1/2/4` 全部变为现行 `10/30/40`。**已完成。**
2. 脚本幂等，可重复执行。**SQL 保留作补刷。**
3. 写入路径不再生成 `1/2/4`。**已满足**（阶段 B 不另立项）。

**非目标**

- 采购/销售订单及明细 `status`
- 扩展进度 `0/1/2`
- `stock_out."Type"`
- 改 `3`（移库）
- 把 `0` / 未知改成 `10`
- 本期删除代码里对历史 `1` 的只读兼容（阶段 C，另排期）

---

## 2. 映射

```text
1 → 10    采购入库 / 销售出库
2 → 30    退货
4 → 40    报废
3 不动    移库
其它不动
```

目标值与源值无交集，三条 `UPDATE … WHERE col = 1|2|4` 不会互相覆盖。仍建议用单条 `CASE`，一次扫描、便于 `GET DIAGNOSTICS`。

---

## 3. 阶段 A — 盘点（只读，先跑）

在目标库执行。把结果贴进变更单，再决定是否刷。

```sql
-- 出入库类型分布（含软删；需要排除软删时自行加 is_deleted = false）
SELECT 'stock_in' AS tbl, "StockInType" AS v, COUNT(*) AS n
FROM public.stock_in GROUP BY 1, 2
UNION ALL
SELECT 'stockin_notify', "StockInType", COUNT(*)
FROM public.stockin_notify GROUP BY 1, 2
UNION ALL
SELECT 'qcinfo', "StockInType", COUNT(*)
FROM public.qcinfo GROUP BY 1, 2
UNION ALL
SELECT 'stock_out', "StockOutType", COUNT(*)
FROM public.stock_out GROUP BY 1, 2
UNION ALL
SELECT 'stockout_notify', "StockOutType", COUNT(*)
FROM public.stockout_notify GROUP BY 1, 2
UNION ALL
SELECT 'packing', "StockOutType", COUNT(*)
FROM public.packing GROUP BY 1, 2
ORDER BY 1, 2;
```

关注：

| 值 | 期望 |
|----|------|
| 1、2、4 | 待刷行数；为 0 则该表可跳过 UPDATE |
| 3 | 移库存量，刷后 **不得减少** |
| 10/20/30/40 | 现行码 |
| 其它 | 记录单号抽查，**不要**纳入本次 UPDATE |

抽查（可选）：各表 `WHERE 类型 IN (1,2,4)` 各取 3～5 个业务单号，确认语义是采购/销售、退货、报废，而不是乱码。

## 4. 阶段 A — 刷新 SQL

生产前：备份或确认 PITR；在从库/副本先跑。

```sql
BEGIN;

UPDATE public.stock_in
SET "StockInType" = CASE "StockInType"
  WHEN 1 THEN 10 WHEN 2 THEN 30 WHEN 4 THEN 40 ELSE "StockInType" END
WHERE "StockInType" IN (1, 2, 4);

UPDATE public.stockin_notify
SET "StockInType" = CASE "StockInType"
  WHEN 1 THEN 10 WHEN 2 THEN 30 WHEN 4 THEN 40 ELSE "StockInType" END
WHERE "StockInType" IN (1, 2, 4);

UPDATE public.qcinfo
SET "StockInType" = CASE "StockInType"
  WHEN 1 THEN 10 WHEN 2 THEN 30 WHEN 4 THEN 40 ELSE "StockInType" END
WHERE "StockInType" IN (1, 2, 4);

UPDATE public.stock_out
SET "StockOutType" = CASE "StockOutType"
  WHEN 1 THEN 10 WHEN 2 THEN 30 WHEN 4 THEN 40 ELSE "StockOutType" END
WHERE "StockOutType" IN (1, 2, 4);

UPDATE public.stockout_notify
SET "StockOutType" = CASE "StockOutType"
  WHEN 1 THEN 10 WHEN 2 THEN 30 WHEN 4 THEN 40 ELSE "StockOutType" END
WHERE "StockOutType" IN (1, 2, 4);

UPDATE public.packing
SET "StockOutType" = CASE "StockOutType"
  WHEN 1 THEN 10 WHEN 2 THEN 30 WHEN 4 THEN 40 ELSE "StockOutType" END
WHERE "StockOutType" IN (1, 2, 4);

COMMIT;
```

刷后再跑 §3 盘点：六表 `1/2/4` 均为 0；`3` 的行数与刷前一致。

若某环境没有 `qcinfo."StockInType"`（极旧库），该句会失败，整事务回滚；先确认列存在再执行。

阶段 A 已在目标库执行。上文 SQL 仅作幂等补刷。创建路径已写 `10/20/30/40` / `3`，不会再落 `1/2/4`。

## 5. 阶段 A — 刷后核对（已通过）

不必全量 Recalculate。抽查即可（2026-08-19 已核对）：

1. 入库列表：原旧 `1` 的单现为采购入库 `10`；「采购入库」页签能筛到。
2. 出库 / 出库通知：原旧 `1` 现为 `10`，进入「销售出库」页签。
3. 移库凭证类型仍为移库（`3`）。
4. 采购明细概况「入库」：已过账采购入库（`10`）仍计入入库完成。
5. 报关入库仍为 `20`，不计入采购行收货。

扩展进度若个别单不一致，用详情「刷新」或现有 Debug 重算该行即可。

---

## 6. 阶段 B — 写入收口（已满足，不另立项）

主创建路径已写 `10/20/30/40` / `3`。入参若仍为 `1/2/4`，`Normalize` / `NormalizeForNotify` 会写成 `10`（不会原样落库；注意此处 `2/4` 也会变成 `10` 而非 `30/40`，但 UI 不提交旧码）。移库内核继续写 `3`。

`Normalize` **本期不改为「未知保持未知」**。前端提交已用 `10/20/30/40`。

---

## 7. 阶段 C — 去掉读兼容（观察后再做）

条件：生产盘点连续一个发布周期 `1/2/4 = 0`。

然后才考虑：

- 删除 `LegacyPurchase` / `LegacySales`
- `IsPurchaseReceipt` / `IsSalesStockOut` 只认 `10`
- 前端 `resolveStockInTypeLabelKey` 不再把 `1` 当采购、`2` 当退货、`4` 当报废（若仍出现则显示「未知」）

未满足条件不要做阶段 C。

## 8. 上线顺序

阶段 A/B **已完成**（2026-08-19）。下文仅作补刷与阶段 C 参考：

1. 目标库跑 §3 确认 `1/2/4 = 0`。  
2. 若仍有残留：备份 → §4 → §3 → §5。  
3. 阶段 C 单独立项（删读兼容）。

回滚：用备份恢复；**不要**把 `10/30/40` 整表还原成 `1/2/4`（会把本来就是新码的行打回旧码）。
