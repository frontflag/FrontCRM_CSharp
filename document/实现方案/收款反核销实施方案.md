## 1. 背景与问题

### 1.1 现状

| 能力 | 付款单 | 收款单 |
|------|--------|--------|
| 强制删除守卫 | `CanForceDeleteFinancePaymentAsync` | `CanForceDeleteFinanceReceiptAsync` |
| 拦截条件 | 明细 `VerificationStatus > 0` 或 `VerificationDone > 0` | 明细 `VerificationStatus > 0` 或 `VerifiedAmount > 0` |
| 反核销 API | `POST .../reverse-verification` ✅ | `POST .../reverse-verification` ✅ |
| 普通 `DELETE` 走守卫 | ✅ 已对齐 | ✅ 已对齐 |

强制删除收款单时，若已做过核销，接口返回：

```text
存在下游业务节点：收款核销明细，不能强制删除收款单
或
存在下游业务节点：销项发票；下游数据单号：{InvoiceCode}
```

与付款单为**同类问题**：须先撤销下游核销，再允许强制删除。

### 1.2 与付款反核销的差异（须在设计中体现）

| 维度 | 付款 | 收款 |
|------|------|------|
| 核销触发 | 「付款完成(100)」**自动**核销全部明细 | 「收款核销工作台」**独立**提交；主单确认后不自动核销 |
| 下游主数据 | 采购订单明细 `FinancePaymentStatus` | 应收款 `finance_receivable` + 核销流水 `finance_receivable_write_off` |
| 审计流水 | 无独立核销流水表 | 有 `finance_receivable_write_off`（详情页已展示） |
| 遗留路径 | 无 | 旧 API `VerifyReceiptItemAsync`（直写销项发票，**不写** write_off 表） |
| 预收池 | 无 | 明细 `AdvancePoolAmount` 可 > 0（**当前守卫未拦截**） |

**术语**：本方案称 **「收款反核销」**，不是「取消」或旧「反审核」。主状态与核销正交（见 [收款单状态](../System/财务/收款单状态-设计与实现.md)）。

## 2. 目标与非目标

### 2.1 目标（本期）

1. 提供 **整单级** 收款反核销：撤销本收款单下全部「收款明细 → 应收款」核销。
2. 反核销后满足 `CanForceDeleteFinanceReceiptAsync`，系统管理员可执行强制删除。
3. 普通 `DELETE` 与强制删除 **共用同一守卫**（与付款对齐）。
4. 回滚销售订单明细收款进度（`SellOrderItemExtendSync`）及销售订单头 `FinanceReceiptStatus`。
5. 操作留痕：业务操作日志 + 关联应收/出库单号摘要。

### 2.2 非目标（本期不做 / 另案）

| 项 | 说明 |
|----|------|
| 单笔核销流水选择性撤销 | 仅支持整单反核销（与付款一致） |
| 预收池核销（write_off_source=20）的撤销 | 来源为预收池，不关联收款单，不在本接口范围 |
| 反审核（旧 2→1、3→2） | **不做**。现网无审核流，也不把确认打回新建 |
| 收款核销工作台 UI 改造 | 仅列表/详情增加反核销入口 |

## 3. 待确认决策点

请产品/业务确认以下 **4 项** 后开工：

### D1. 主单状态是否回滚？

| 选项 | 说明 |
|------|------|
| **A（推荐）** | **不回滚** `Status`：已审核(2)/已收款(3) 保持不变，仅清空明细核销字段 |
| B | 若当前为已收款(3)，反核销后 **3→2**（与付款 100→10 对称） |

**推荐 A 理由**：核销可在「已审核」阶段完成；「已收款」表示来款确认，与应收核销是不同维度。

### D2. 预收池余额（`AdvancePoolAmount > 0`）如何处理？

| 选项 | 说明 |
|------|------|
| **A（推荐）** | 反核销 **不处理** 预收池；**同步增强强制删除守卫**：`AdvancePoolAmount > 0` 时拦截，提示「须先回滚预收池入账」；预收池回滚另做 **「反预收入账」** 小接口（可二期） |
| B | 反核销 **捆绑** 回滚本单全部 `AdvancePoolAmount`（冲减客户预收余额 + 写负向流水） |

**推荐 A 理由**：预收池是客户维度余额，与「核销到应收」业务语义不同；拆开更安全。

### D3. 遗留路径 `VerifyReceiptItemAsync` 是否覆盖？

| 选项 | 说明 |
|------|------|
| **A（推荐）** | **覆盖**：无 `finance_receivable_write_off` 但 `VerifiedAmount > 0` 时，按明细关联的 `FinanceSellInvoiceId` 回滚销项发票 `ReceiveDone/ReceiveToBe`，并清零明细 |
| B | 仅支持新链路（有 write_off 记录）；遗留数据走 SQL 人工处理 |

**推荐 A 理由**：API 仍存在（`POST .../items/{id}/verify`），需防历史数据卡死。

### D4. 核销流水 `finance_receivable_write_off` 保留策略？

| 选项 | 说明 |
|------|------|
| **A（推荐）** | **物理删除** 本单关联的 ReceiptItem 来源流水；完整明细写入 **操作日志**；核销流水页不再展示（管理员纠错场景，频次极低） |
| B | 新增 `is_reversed` 字段，软标记保留审计（需迁移） |
| C | 插入负金额「冲销流水」保留双边记录（实现最重） |

**推荐 A 理由**：与付款「重置字段、无独立流水表」的简洁性一致；操作日志补足审计。

> **2026-08-17 落地变更**：流水改为与进项发票一致的 **软删**（`is_deleted` + 查询过滤器）。上表 D4-A 为 2026-07-09 历史决策；现行口径见 [付款收款反核销-设计与实现](../System/财务/付款收款反核销-设计与实现.md) 与 [关系表与核销流水软删除](../System/系统/关系表与核销流水软删除-设计与实现.md)。

## 4. 业务规则

### 4.1 前置条件（全部满足才可反核销）

| # | 规则 |
|---|------|
| P1 | 收款单存在且未软删 |
| P2 | `confirmBillCode` 与 `FinanceReceiptCode` 完全一致 |
| P3 | 主状态为确认（`3`，历史 `2`）；新建/取消不可 |
| P4 | 存在可撤销核销：任一明细 `VerificationStatus > 0` 或 `VerifiedAmount > 0`，**或** 存在 `write_off_source=10` 且关联本单的 `finance_receivable_write_off` |
| P5 | （若采用 D2-A）任一明细 `AdvancePoolAmount > 0` → **拒绝**，提示先处理预收池 |
| P6 | 财务数据非只读（与付款一致，`RejectIfFinanceDataReadOnlyAsync`） |

### 4.2 反核销执行效果（确认后实现）

对每条本单关联的 **ReceiptItem 来源** 核销流水（按 `CreateTime` 倒序处理，避免中间态不一致）：

1. **应收款** `FinanceReceivable`  
   - `VerifiedDone -= Amount`  
   - `VerifiedToBe = max(0, Amount - VerifiedDone)`（与正向 `ApplyWriteOffAsync` 对称）  
   - `VerificationStatus = FinanceVerificationStatusCode.Resolve(Amount, VerifiedDone)`

2. **收款明细** `FinanceReceiptItem`  
   - `VerifiedAmount -= Amount`（按流水聚合到对应 `FinanceReceiptItemId`）  
   - `VerificationStatus = Resolve(ReceiptConvertAmount, VerifiedAmount)`

3. **核销流水**  
   - 删除该 `finance_receivable_write_off` 行（D4-A）

4. **遗留路径收尾**（D3-A）  
   - 若某明细 `VerifiedAmount` 仍 > 0（无 write_off 的纯遗留核销）：  
     - 销项发票：`ReceiveDone -= VerifiedAmount`，`ReceiveToBe += VerifiedAmount`，重算 `ReceiveStatus`  
     - 同步销项发票明细 `ReceiveStatus`  
     - 明细 `VerifiedAmount = 0`，`VerificationStatus = 0`

5. **销售订单**  
   - 收集受影响 `SellOrderItemId`，调用 `SellOrderItemExtendSync.RecalculateAsync`  
   - 对受影响 `SellOrderId` 重算 `FinanceReceiptStatus`（复用 `SyncSellOrderReceiptStatusAsync` 逻辑）

6. **主单**（D1-A）  
   - 仅更新 `ModifyTime` / `ModifyByUserId`，**不改** `Status`、`ReceiptAmount`、`ReceiptDate`

7. **操作日志**  
   - `BizType = FinanceReceipt`  
   - `ActionType = 收款反核销`（新增常量）  
   - 摘要含：收款单号、撤销流水笔数、关联应收号/出库号（最多展示 5 个）

### 4.3 反核销后的强制删除链路

```text
已核销收款单
  → POST /api/v1/finance/receipts/{id}/reverse-verification  （finance-receipt.write）
  → POST /api/v1/finance/receipts/{id}/force-delete          （SYS_ADMIN + finance-receipt.write）
```

### 4.4 强制删除守卫增强（建议本期一并做）

在 `CanForceDeleteFinanceReceiptAsync` 增加：

```text
任一明细 AdvancePoolAmount > 0 → 拒绝
提示：存在下游业务节点：客户预收池入账；须先回滚预收池后再删除
```

（与 D2-A 配套；若选 D2-B 则改为反核销内处理，守卫仅看核销字段。）

## 5. API 契约

### 5.1 反核销

```http
POST /api/v1/finance/receipts/{id}/reverse-verification
Authorization: Bearer …
Permission: finance-receipt.write
```

**Request Body**

```json
{
  "confirmBillCode": "REC00001"
}
```

**Response 200**

```json
{
  "success": true,
  "message": "反核销成功",
  "data": { /* FinanceReceipt 含 Items */ }
}
```

**错误码**

| HTTP | 场景 |
|------|------|
| 400 | 未填 `confirmBillCode`、确认单号不匹配、无需反核销、存在预收池余额（D2-A） |
| 403 | 未登录、无写权限、财务只读 |
| 409 | 状态不允许（非 2/3）、收款单不存在等业务冲突 |
| 500 | 未预期异常 |

### 5.2 普通删除对齐

`DELETE /api/v1/finance/receipts/{id}` 在 `DeleteAsync` 内增加 `CanForceDeleteFinanceReceiptAsync` 校验，错误文案与强制删除一致。

| 层 | 职责 |
|----|------|
| `IFinanceReceivableService.ReverseWriteOffsByReceiptAsync` | 核心回滚：write_off、receivable、receiptItem、遗留销项发票 |
| `IFinanceReceiptService.ReverseVerificationAsync` | 确认单号、前置校验、调用上层、写操作日志、返回 enriched receipt |

`OperationLogActionTypes.FinanceReceiptReverseVerification = "收款反核销"`

### 8.3 事务
