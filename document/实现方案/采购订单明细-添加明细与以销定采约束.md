# 采购订单明细「添加明细」与以销定采约束

> **背景**：采购订单明细通过 `SellOrderItemId` 挂接销售订单明细，是以销定采、采购申请状态回写、销单已采购量、客单库存分桶的核心字段。  
> 若在 **客单采购** 主单上通过「添加明细」手工增加 **无销售行关联** 的明细，会导致 PR/销单/库存链条断裂。  
> **实施日期**：2026-07-03（与多 PR 合并生成 PO、列表篮子联调同期落地）。

**关联文档**：

- 《[新建采购订单 PRD](../PRD/业务功能/采购订单/新建采购订单PRD.md)》— 操作入口与数据来源  
- 《[业务逻辑与数据关系文档](../System/业务逻辑与数据关系文档.md)》§1.3 / §7.2 — 销售-采购外键与数据流  
- 《[销售订单明细-添加明细与报价溯源约束](../实现方案/销售订单明细-添加明细与报价溯源约束.md)》— 上游 SO 对 `QuoteId` 的镜像约束（已实施，2026-07-03）

## 1. 数据模型要点

| 层级 | 字段 | 说明 |
|------|------|------|
| `purchaseorder.Type` | `1` 客单 / `2` 备货 / `3` 样品 | 主单类型；保存时由明细是否含销售关联 **重算**，非仅信前端下拉 |
| `purchaseorderitem.SellOrderItemId` | 可空 FK → `sellorderitem` | **以销定采唯一落库关联**；备货/手工行存 `NULL` |
| `purchaserequisition` | `SellOrderItemId` / `SellOrderId` | PR 不写在 PO 行上；通过同一 `SellOrderItemId` **反查** PO 并重算状态 |

**不存在** `PurchaseRequisitionId` 于 `purchaseorderitem` 表。

**前端占位 GUID**（无销售行时传入、后端视为未关联）：

`00000000-0000-0000-0000-000000000000`

---

## 2. 订单类型解析规则（保存时）

与 `CRM.Core.Utilities.PurchaseOrderItemLinkRules.ResolveHeaderType` 一致：

| 明细情况 | 落库主单 `Type` |
|----------|-----------------|
| **任一行** 有有效 `SellOrderItemId` | `1` 客单采购 |
| **全部** 无销售关联，且请求为样品 | `3` 样品采购 |
| **全部** 无销售关联，且非样品 | `2` 备货采购 |

> 因此：纯手工明细即使用户界面曾显示「客单」，保存后头表也会变为 **备货**；真正危险的是 **混合单**（部分有 `SellOrderItemId`、部分无）导致头表为客单而部分行断链。

---

## 3. 约束条件总览

| # | 约束 | 层级 | 行为 |
|---|------|------|------|
| C1 | 客单采购 **禁止** 手工「添加明细」 | 前端 UI | `type === 1` 时隐藏「添加明细」按钮 |
| C2 | 客单采购 **至少保留 1 条** 明细 | 前端 UI | 仅 1 行时隐藏「删除」；删最后一条时 Toast 拦截 |
| C3 | 客单采购 **每条明细** 须有 `SellOrderItemId` | 前端保存前 | 校验失败 → `ElMessage.warning`，不提交 |
| C4 | 同上 | 后端 API | `CreateAsync` / `UpdateAsync`（含明细）→ `ArgumentException`，事务不落库 |
| C5 | 客单 PO 入库行无销售关联 | 入库过账 | 库存 `StockType` **按备货(2)入账** + `LogWarning`（历史脏数据兜底） |

**未纳入本次**（可后续迭代）：历史脏数据批量巡检/修复脚本。

## 4. 入口与「添加明细」可见性

### 4.1 页面

- **组件**：`CRM.Web/src/views/RFQ/PurchaseOrderCreate.vue`  
- **路由**：`PurchaseOrderCreate`（新建）、`PurchaseOrderEdit`（编辑，同组件）

### 4.2 操作入口对照

| 入口 | 典型 `Type` | 「添加明细」 |
|------|-------------|--------------|
| 采购申请列表/详情 → 生成采购订单 | `1` 客单（预填行带 `SellOrderItemId`） | **隐藏** |
| 采购订单列表 → 新建备货 `?type=2` | `2` 备货 | **显示** |
| 编辑已有客单 PO | `1` | **隐藏** |
| 编辑已有备货/样品 PO | `2` / `3` | **显示** |

### 4.3 预填行数据来源

从 PR 进入时，`buildPoLineItemFromPr` 将 PR 的 `sellOrderItemId` 写入明细草稿；**不**写入 PR 主键。

## 5. 实现方式

### 5.1 共享规则（前后端对齐）

| 位置 | 文件 |
|------|------|
| 后端 | `CRM.Core/Utilities/PurchaseOrderItemLinkRules.cs` |
| 前端 | `CRM.Web/src/utils/purchaseOrderItemLinkRules.ts` |

主要 API：

- `IsLinkedSellOrderLine` / `isLinkedSellOrderItemId` — 是否有效销售行关联  
- `ResolveHeaderType` / `resolvePoHeaderType` — 头表类型解析  
- `ValidateCustomerOrderItems` / `validateCustomerOrderItemsForSave` — 客单保存校验  
- `ResolveInboundStockType` — 入库库存类型兜底  

### 5.2 前端 UI 与保存

**计算属性**（`PurchaseOrderCreate.vue`）：

```ts
allowAddPoItem   // type !== 1 → 显示「添加明细」
canRemovePoItem  // type !== 1 或 items.length > 1 → 显示「删除」
```

**保存流程**（在品牌校验之后、API 之前）：

1. `validatePoItemsCustomerOrderLinks()`  
2. 失败 → `t('purchaseOrderCreate.validate.*')` 提示，中止  

**`addItem()`** 行为（备货/样品仍可用）：新建行 `sellOrderItemId: undefined`；与客单场景已通过 C1 屏蔽。

### 5.3 后端保存

**文件**：`CRM.Core/Services/PurchaseOrderService.cs`

在 `ResolvePurchaseOrderHeaderType` 之后：

```csharp
PurchaseOrderItemLinkRules.ValidateCustomerOrderItems(
    headerType,
    request.Items.Select(i => i.SellOrderItemId).ToList());
```

- **创建**：`CreateAsync`  
- **更新**：`UpdateAsync` 且 `request.Items` 非空时（与明细同步后、`order.Type` 已重算）

错误文案（中文）：

- `客单采购订单至少需要一条明细`  
- `客单采购订单的第 {n} 条明细须关联销售订单明细`  

### 5.4 入库二次校验（兜底）

**文件**：`CRM.Core/Services/InventoryCenterService.cs`

`PostStockIn` 内 **按入库行** 调用 `ResolveInboundStockTypeForLineAsync`：

- 读取 PO 头 `Type` 与行上 `SellOrderItemId`（入库扩展 + 采购明细）  
- 头为客单(1) 且行无销售关联 → `StockType = 2`（备货），并写 Warning 日志  
- 避免「客单类型库存但不绑定任何销单行」

## 7. 风险场景对照

| 场景 | 约束后结果 |
|------|------------|
| 客单 PO 点「添加明细」 | 按钮不可见（C1） |
| 客单 PO 删掉所有行再保存 | 删至 1 行后不可删（C2）；若强行提交 0 行由既有「至少一条明细」拦截 |
| 客单 PO 混合有/无 `SellOrderItemId` | 保存被拒（C3/C4） |
| 历史坏单入库 | 按备货入账（C5），日志可追溯 |
| API 直连绕过前端 | 后端 C4 拦截 |
