## 1. 测试目标与范围

### 1.1 测试目标

验证销售订单详情页的六分面刷新功能满足产品设计要求：

1. 每个分面只处理声明范围内的下游字段，不污染其它分面。
2. 源字段（客户 ID、物料型号、客户料号、品牌、客户品牌、数量、单价）在刷新过程中不被修改。
3. 已完结节点按销售参数分面开关正确门控，确认后才可覆盖。
4. 刷新型号 / 品牌**只**改销售身份快照，**不换库存堆、不改库存明细编号、不重算备货可用量**。
5. 权限、数据范围、金额脱敏、API 契约、前端交互符合预期。

### 1.2 测试范围

| 范围项 | 说明 |
|--------|------|
| 包含 | 销售订单详情页「刷新状态」主按钮及下拉五项；`POST /refresh`、`POST /refresh/preview`、销售参数「分面刷新」开关 |
| 不包含 | 销售订单列表 / 明细列表的「刷新」重查、浏览器 F5、「刷新全部」（无入口）、库存换堆 / 删除空汇总（销售不做） |
| 重点关注 | 分面隔离、已完结预检与确认、销售身份快照同步、数量不收缩已出库通知 |

### 1.3 测试策略

| 测试类型 | 覆盖方式 | 比例建议 |
|----------|----------|----------|
| 单元 / 服务自动化 | `SalesOrderRefreshCompletedGateService`、`SalesOrderIdentityDownstreamSyncService`、`SellOrderItemExtendSyncService`、`SalesOrderSalesPriceDownstreamSyncService`、`SalesOrderCustomerDownstreamSyncService` | 核心 |
| API 契约测试 | `refresh`、`refresh/preview`、`sync-downstream-customer`、`refresh-completed-facets` 接口的边界、权限、参数校验 | 高 |
| 前端 UI 测试 | 按钮状态、确认框、结果弹窗、下拉项显隐 | 中 |
| 集成 / 端到端测试 | 从详情页点击到下游单据数据一致性的完整链路 | 高 |
| 回归测试 | 保存销售明细、换客户、收款核销、开票匹配、Debug 刷新状态 | 高 |

## 3. 测试入口、退出与风险

### 3.1 准入条件

- 后端 API 与前端页面已部署到测试环境。
- 销售参数「分面刷新」五个开关可正常读写。
- 测试数据已构造：含单条 / 多条出库通知、已出库、已装箱出库完成、已核销应收、已开票等场景。

### 3.2 退出条件

- 本方案中 P0 / P1 用例 100% 执行通过。
- 无阻塞性缺陷（Severity 1）。
- 已发现的 P2 缺陷有明确的修复计划或接受记录。

### 3.3 风险与应对

| 风险 | 影响 | 应对 |
|------|------|------|
| 销售与采购实现差异点多 | 直接照搬采购用例会遗漏差异 | 严格对照「与采购的差异表」逐条验证 |
| 已完结判定口径多 | 参数开关与预检结果不一致 | 对照 §8 判定表逐条核对 |
| 客户刷新涉及已核销应收 / 已开票销项 | 容易误判为应改客户 | 验证这些单据不进覆盖列表且客户字段不变 |
| 装箱主表型号/品牌后执行者生效 | 采购与销售刷新相互覆盖 | 构造交叉场景验证最终值 |
