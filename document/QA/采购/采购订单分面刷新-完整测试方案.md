## 1. 测试目标与范围

### 1.1 测试目标

验证采购订单详情页的六分面刷新功能满足产品设计要求：

1. 每个分面只处理声明范围内的下游字段，不污染其它分面。
2. 源字段（供应商 ID、物料型号、品牌、数量、单价）在刷新过程中不被修改。
3. 已完结节点按采购参数分面开关正确门控，确认后才可覆盖。
4. 刷新型号 / 品牌时库存分桶键正确重对齐，空旧堆安全清理，库存明细编号不变。
5. 权限、数据范围、金额脱敏、API 契约、前端交互符合预期。

### 1.2 测试范围

| 范围项 | 说明 |
|--------|------|
| 包含 | 采购订单详情页「刷新状态」主按钮及下拉六项；`POST /refresh`、`POST /refresh/preview`、采购参数「分面刷新」开关 |
| 不包含 | 采购订单列表 / 明细列表的「刷新」重查、浏览器 F5、「刷新全部」（无入口） |
| 重点关注 | 分面隔离、已完结预检与确认、库存换堆与空汇总清理、源字段只读 |

### 1.3 测试策略

| 测试类型 | 覆盖方式 | 比例建议 |
|----------|----------|----------|
| 单元 / 服务自动化 | `PurchaseOrderRefreshCompletedGateService`、`PurchaseOrderItemExtendSyncService`、`PurchaseOrderIdentityDownstreamSyncService`、`StockItemPurchaseIdentityRebucketService`、`PurchaseOrderPurchasePriceDownstreamService`、`PurchaseOrderVendorChangeService` 等 | 核心 |
| API 契约测试 | `refresh`、`refresh/preview`、`refresh-completed-facets` 接口的边界、权限、参数校验 | 高 |
| 前端 UI 测试 | 按钮状态、确认框、结果弹窗、下拉项显隐 | 中 |
| 集成 / 端到端测试 | 从详情页点击到下游单据数据一致性的完整链路 | 高 |
| 回归测试 | 保存采购明细、换供应商、进项匹配、付款核销、Debug 刷新状态 | 高 |

## 3. 测试入口、退出与风险

### 3.1 准入条件

- 后端 API 与前端页面已部署到测试环境。
- 采购参数「分面刷新」五个开关可正常读写。
- 测试数据已构造：含单批次 / 多批次到货、已入库、已过账、已付款、已进项匹配、库存换堆等场景。

### 3.2 退出条件

- 本方案中 P0 / P1 用例 100% 执行通过。
- 无阻塞性缺陷（Severity 1）。
- 已发现的 P2 缺陷有明确的修复计划或接受记录。

### 3.3 风险与应对

| 风险 | 影响 | 应对 |
|------|------|------|
| 库存换堆涉及多表，数据构造复杂 | 遗漏边界 | 与开发共同准备最小可复现数据集；每类换堆至少一组 |
| 已完结判定口径多 | 参数开关与预检结果不一致 | 对照 §8 判定表逐条核对 |
| 旧接口 `refresh-item-extends` 兼容 | 误改既有行为 | 增加回归用例，确保等价 `facet=price` |
